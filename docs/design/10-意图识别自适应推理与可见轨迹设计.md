# 10 意图识别自适应推理与可见轨迹设计

## 1. 目标与范围

本设计重构 ChatUI 的意图识别链路，目标是同时满足：

1. 简单请求保持低延迟；复杂请求增加必要的语义推理预算；
2. 上下文、资源、历史任务和当前输入形成单一、可追溯的语义证据；
3. 只有会改变执行语义的歧义才触发澄清；
4. 对结构错误、语义矛盾和遗漏要求分别执行有界自修复；
5. 意图识别过程中向用户展示结构化决策轨迹，终态默认收起且可恢复查看。

本次不改变聊天、文件、图片、代理和任务执行 API 的既有能力集合；`route_intent.v3` 继续是最终路由语义合同，`dispatch_contract.v1` 继续是唯一执行授权边界。

不展示或持久化模型的原始私有思维链。用户看到的是由阶段状态、证据摘要、决策结果和校验结果组成的 `intent_reasoning.v1` 结构化轨迹；原始模型输出仍按现有脱敏规则处理。

## 2. 根因与设计取舍

当前理解节点使用 `noReasoning: true`，理解结果只包含 `dependency` 与 `actions`，理解失败后路由仍会继续；路由修复主要检查 schema 和局部矛盾，不能发现“结构合法但遗漏用户要求”的结果。本设计不通过继续堆叠单一巨型提示词解决问题，而采用自适应深度和单一语义证据链。

速度与质量取舍如下：

- 低风险请求：保持一次结构化路由调用，不执行深度理解和语义审查；
- 高风险请求：执行理解、路由和语义审查；只有审查失败才进行定向修复；
- 传输错误、配置错误、取消和超时仍按既有失败分类处理；
- 任何模型或本地阶段都不得越过最终 dispatch contract 自动执行。

### 2.1 单附件请求的廉价路径

单个当前图片或文件作为本轮回答证据时，不因附件存在本身触发理解节点；只有多资源、明确指代/跨轮依赖或多动作等语义复杂度才升级到理解路径。这样普通的“根据这张图回答/输出方案”保持一次路由调用，避免无必要的 understanding、critic 和规划调用串行叠加。

## 3. 状态机与流程

```text
captured
  -> context_ready
  -> fast_route
  -> risk_assessed
      -> low_risk -> route_validated -> ready
      -> high_risk -> understood -> route_compiled -> semantically_checked
                                      |                 |-> repair -> semantically_checked
                                      |                 |-> clarify
                                      |                 |-> ready
                                      |-> failed
```

每个请求共享一个绝对 deadline 和 attempt ledger。阶段只能前进或进入明确的 `repair`、`clarify`、`failed` 终态，不允许无限循环。

## 4. 内部语义证据合同

新增内部版本化合同 `semantic_intent.v1`，不直接作为执行授权：

```json
{
  "schema_version": "semantic_intent.v1",
  "goal": "用户本轮要达成的结果",
  "claims": [
    {"id":"c1","text":"用户明确要求的事实或约束","polarity":"must","source":"current_input"}
  ],
  "actions": [
    {
      "id":"a1",
      "kind":"image_generate",
      "target":"具体目标",
      "must":["必须保留的约束"],
      "must_not":["明确禁止的约束"],
      "resource_refs":[],
      "depends_on":[],
      "output":"结果说明"
    }
  ],
  "ambiguities": [],
  "assumptions": [],
  "success_criteria": []
}
```

约束：

- `claims` 必须能回指当前输入、quoted、已确认上下文或确定性应用状态；
- `assumptions` 只能包含用户明确授权的委托性补全；
- 不确定资源不得由模型猜成确定资源；
- operation、角色和最终执行参数仍由 `route_intent.v3` 与本地合同校验决定；
- `depends_on` 只描述语义依赖，不授予工具或执行权限。

### 4.1 理解节点与路由节点的权责

`intent_understanding.v1` 的 action kind 是语义理解证据，不得在无新增资源事实、无明确协议冲突时被本地关键词规则重新映射为另一个 operation。资源事实只允许校正资源绑定能力（例如明确绑定 `fN` 时将资源任务从 `plain_text` 归类为 `file_read`）；不能用“总结/分析/然后”等词推断用户已经提供了待处理文件或正文。

“下面这段话”“以下内容”等指代未兑现时，应由输入完整性与理解契约共同产生 `business_clarification`，澄清缺失的正文来源；不得把缺失正文伪装成文件资源缺失。

## 5. 语义审查合同

新增内部 `intent_critic.v1`：

```json
{
  "schema_version":"intent_critic.v1",
  "verdict":"accept|repair|clarify|reject",
  "covered_claims":[{"claim_id":"c1","action_ids":["a1"]}],
  "missing_claims":[],
  "conflicts":[],
  "unsupported_assumptions":[],
  "ambiguous_bindings":[],
  "reasons":[{"code":"...","field":"...","message":"..."}]
}
```

`accept` 的必要条件：

- 所有必须 claim 均被一个或多个 action 覆盖；
- 无未授权假设；
- 无资源角色、relation、goal_mode 或任务依赖冲突；
- 澄清状态为空或仅包含非阻塞可选信息；
- 最终路由仍通过既有 `route_intent.v3` 和 `dispatch_contract.v1` 校验。

## 6. 可见推理轨迹

新增 `intent_reasoning.v1`，只存结构化摘要：

```json
{
  "schema_version":"intent_reasoning.v1",
  "status":"running|ready|clarify|failed|hidden",
  "steps":[
    {
      "id":"s1",
      "stage":"context|risk|understanding|grounding|routing|checking|repair|clarification|completed|failed",
      "status":"pending|running|completed|failed",
      "summary":"正在确认本轮引用的是当前图片",
      "evidence":["current_input","i2"],
      "decision":"image_edit",
      "reason_codes":[]
    }
  ],
  "final_summary":"..."
}
```

默认行为：

- 路由进行中显示步骤和当前摘要；
- `ready`、`clarify` 或 `failed` 后默认折叠轨迹；
- 用户可展开查看本轮结构化摘要；
- 不显示原始 prompt、API key、完整模型输出、隐藏身份或私有 reasoning token；
- 页面刷新或任务恢复时只恢复脱敏后的阶段摘要和终态，不恢复运行中的假状态。

## 7. 自适应成本策略

风险信号包括：跨轮指代、quoted、否定/纠正、多个动作、条件句、多个候选资源、任务依赖、已存在澄清、超长约束和模型初次校验失败。

- 低风险：一次 route 调用；
- 中风险：一次 route 调用（复杂度 gate 已覆盖指代、quoted、多动作等需要理解节点的高价值场景；其余中风险信号由确定性 operation/relation/goal-mode 政策收窄）；
- 高风险：一次理解 + 一次 route + 独立 critic（生产路径启用）；
- repair 仅重跑失败阶段，最多两轮；
- reasoning 参数仅在高风险阶段启用，低/中风险保持关闭；
- 所有阶段共享现有绝对 deadline，禁止为每个节点重新开启完整超时窗口。

## 8. 安全、错误和兼容

- `route_intent.v3` 和 `dispatch_contract.v1` 不降级；
- 无效模型输出、配置错误、网络错误、超时和取消继续分别分类；
- 本地逻辑只可补充确定性事实或执行不变量，不能静默替换模型语义；
- 所有语义修改保留 `model_proposal`、`normalized_proposal` 和 `normalization_changes` 的来源；
- 轨迹内容必须经过统一脱敏，不写 API key、Authorization、Base64、签名 URL 或完整二进制；
- 新的 requestPurpose、schema 和日志字段必须进入服务端白名单和审计。

## 9. 验收标准

1. 现有全部单元和 smoke 测试通过；
2. 简单请求维持单次模型调用路径；
3. 高风险请求能展示阶段轨迹，终态默认折叠且可重新展开；
4. 结构合法但遗漏用户要求的路由必须被 critic 拦截；
5. 不必要的 clarification 必须被识别并修复或转为 ready；
6. 语义错误必须优先自动修复，达到上限后才向用户澄清或失败；
7. 模型原始输出与最终路由的任何语义差异可追溯；
8. 评测 fixture 的每个场景分别由每个意图模型完整运行；
9. `gpt-5.6-luna` 的所有场景得分、合法合同率和 safety-critical perfect rate 均为 100%；
10. 评测报告不包含凭据、Base64、原始完整模型输出或生成日志。

## 10. 回归测试清单

- reasoning 阶段在简单/复杂请求上的自适应选择；
- understanding 失败不会静默伪装成 ready；
- claim 漏项、禁止项丢失、动作依赖丢失；
- 不必要澄清和真正阻塞澄清；
- model proposal 与 normalization provenance；
- 轨迹更新、终态折叠、展开和刷新恢复；
- 取消、超时、fallback、repair 预算和 deadline；
- 三个模型的完整 fixture 评测、差异报告和 Luna 100% 门禁。

## 11. 当前落地状态（2026-08-29）

已落地的第一阶段实现：

- `shared/intent-reasoning.js` 提供有界轨迹、风险信号、reasoning summary 提取和脱敏；
- `shared/intent-claims.js` 提供显式选择、排除、图片排名、历史文字和独立输出要求的通用证据；
- `shared/semantic-intent.js` 把 current input、claims 与 understanding actions 合成为 `semantic_intent.v1` 中间语义证据，供 route 与 critic 共用；
- `shared/intent-critic.js` 提供本地语义覆盖审查及 `intent_critic.v1` 合同；高风险生产路径再调用独立 critic 模型；
- route payload 默认保持 no-reasoning 快路径，高风险路径启用中等 reasoning summary；
- 确定性 operation/relation/goal-mode policy 先进入模型 payload，生产工作流显式 enforcement，直接模型评测保持 raw oracle；
- 意图轨迹在路由期间显示为可折叠结构化步骤，终态默认收起；
- `scripts/evaluate-intent-models.js` 对每个意图模型逐场景运行完整 fixture，并同时报告 raw route 与最终 pipeline 结果、调用次数和延迟。

该阶段不把本地规则当作无界语义兜底：只有由当前输入、候选目录或已验证应用状态唯一证明的 policy 才能自动收窄；其余语义错误进入 critic/repair，仍无法确认时保持澄清或失败关闭。


## 11. 等待态可见性与可理解性

意图识别尚未完成时，用户看到的状态必须同时满足：

- 使用“正在理解你的请求”等面向用户的自然语言，不直接暴露“意图模型”“路由”等内部术语；
- 通过状态圆点和省略号动效明确表示仍在工作，避免用户误以为界面卡住；
- 终态使用“已理解你的请求”，并保留可折叠的阶段轨迹；
- 遵循 `prefers-reduced-motion`，减少动效用户不播放等待动画。
- 统一 live surface 内完整展示 `intent_reasoning.v1` 的每个结构化步骤，包括阶段摘要、决策和证据；不再用友好文案折叠掉步骤内容。
- 带计时器的执行等待行（如“正在生成图片 已等待 12 秒”）在同一个 surface 内覆盖更新，不新增第二行或第二个 assistant 节点。
- 呼吸动效只落在当前正在进行的步骤上；历史步骤保持静态，终态默认折叠。

这只是展示层变化，不改变 `route_intent.v3`、执行授权或失败分类。
- 等待态只允许一个统一 live surface；不得同时渲染“正在处理你的请求”和 operation 专属等待文案。阶段状态应原位更新，不能通过新增第二个 assistant 状态节点并排显示。
- 等待态使用单行状态显示；新的阶段状态直接覆盖旧状态，不并排保留多个等待提示，不把执行等待文案追加到意图轨迹中。


## 12. 基线路由与受限修复（2026-08-30）

`route_intent.v3` 首次通过严格 schema 和本地编译后，是后续审查与修复的**可信基线**。语义审查只能提出字段级问题，不能把没有确定性证据的“未使用历史消息”当作错误；尤其不能因为用户没有出现“上一条消息”等固定关键词，就否定合法的 `mN=context` 绑定。

路由修复改用内部 `route_repair.v1` 协议，而不是让修复模型重新输出并替换整份 `route_intent.v3`：

```json
{
  "schema_version": "route_repair.v1",
  "changed_fields": ["relation"],
  "operation": "plain_chat",
  "relation": "followup",
  "goal": "...",
  "goal_mode": "replace",
  "resource_refs": [{"candidate_key":"m1","role":"context"}],
  "task_shape": "single"
}
```

约束如下：

- 修复请求携带不可变的 `base_route_intent`、候选目录、字段级 `reasons` 和 `allowed_fields`；
- `changed_fields` 是修复权限清单；未声明字段必须与基线逐值一致；
- 本地编译器只将声明且被原因授权的字段合并回基线；
- 没有 `resource_refs` 修复理由时，不得删除、改选或清空已有资源绑定；
- 兼容只会返回完整 v3 路由的网关时，本地先从完整输出推导差异，再应用同一字段权限校验，绝不整体替换基线；
- 修复结果越权、漏报变化或不合法时，保留原始基线并最多重试一次；仍失败则以 `invalid_model_output` 失败关闭，绝不执行被破坏的路由；
- 对 text-focused 请求，资源策略可禁止图片/文件，但若候选目录存在消息，仍允许模型在正文确有依赖时选择 `message=context`；“没有固定关键词”不是禁止消息绑定的证据。

验收回归：已正确绑定历史 Markdown 表格消息的 follow-up 必须直接 `ready`，不进入 repair；若错误修复输出试图删除该消息绑定，必须被拒绝且没有 dispatch contract。
