## 1. 使用说明

### 1.1 状态定义

- `PASS`：实际行为与预期一致，且证据完整。
- `FAIL`：产品行为与预期不一致，必须记录缺陷。
- `BLOCKED`：服务、浏览器或网络环境阻断用例执行。
- `SKIP`：当前环境明确缺少对应模型或故障注入能力。
- `NOT RUN`：尚未执行。

`SKIP` 只能用于环境确实不具备的能力，例如没有图片编辑模型、mask 能力或可断开 SSE 的测试网关。已经具备能力但执行失败时必须记为 `FAIL`。

每条用例执行后填写：

```text
状态：PASS / FAIL / BLOCKED / SKIP / NOT RUN
实际结果：
证据：截图、录屏、Network 请求、Console、Job ID
缺陷编号：
执行人：
执行时间：
```

### 1.2 通用执行规则

1. 除非用例明确要求连续上下文，否则每条用例使用新会话。
2. 自动意图相关用例必须使用“自动路由”模式。
3. 每条意图用例开始前清空 Network，开启 `Preserve log`。
4. 文本答案除固定标记外不要求逐字一致，但事实、资源和任务类型必须一致。
5. 图片结果不要求像素级一致；以最终请求参数、资源角色和必须出现的视觉元素为准。
6. 不得在截图、测试记录或缺陷描述中粘贴真实 API Key。
7. 本地服务必须使用端口 `8765`，不能自动改用其他端口。
8. 如果 `8765` 无法访问，先确认监听进程；不要在其他端口启动第二个实例。

## 2. 测试准备

### 2.1 必需模型能力

| 别名 | 能力 | 用途 |
|---|---|---|
| C1 | 支持流式聊天 | 普通聊天、停止和刷新恢复 |
| C2 | 与 C1 不同的聊天模型 | 会话模型隔离 |
| T1 | 意图识别模型 | 自动路由和澄清 |
| R1 | 支持 reasoning | 思考模式，可选 |
| I1 | 支持 `/images/generations` | 文本生图 |
| I2 | 支持 `/images/edits` | 图片编辑、多图和 mask |
| G1 | 可控制延迟、断流和图片响应格式的测试网关 | 故障及兼容测试，可选 |

如果没有独立 T1，将路由模型留空，验证它是否跟随当前聊天模型。

### 2.2 图片夹具

| 编号 | 文件 | 固定内容 |
|---|---|---|
| IMG-A | `target-red-mug.png` | 白色桌面中央一个红色杯子，右下角写 `TARGET-A` |
| IMG-B | `content-blue-bike.jpg` | 蓝色自行车，左上角写 `CONTENT-B` |
| IMG-C | `style-watercolor.png` | 明显水彩画风，写 `STYLE-C` |
| IMG-M | `transparent-mask.png` | 与 IMG-A 同尺寸；杯子区域透明，其余不透明 |
| IMG-P1 | `product-a.png` | 产品图 A，写 `PRODUCT-A` |
| IMG-P2 | `product-b.png` | 产品图 B，写 `PRODUCT-B` |

| IMG-BMP | `sample.bmp` | 正常 BMP 图片 |

### 2.3 Network 协议基线

#### 意图识别阶段

请求必须包含：

```json
{
  "requestPurpose": "intent_recognition"
}
```

请求不得包含：

```text
dispatchContract
bindingEvidence
图片二进制
图片 Base64
```

#### 最终执行阶段

请求必须包含：

```json
{
  "requestPurpose": "final_execution",
  "dispatchContract": {
    "schema_version": "dispatch_contract.v1"
  },
  "bindingEvidence": []
}
```

#### 本地编译边界

路由模型只返回 `operation`、`relation`、`goal`、`resource_refs` 四字段 `route_intent.v1`。`goal` 描述消歧后的用户目标；协议没有重复版本字段，也没有 API、最终执行参数、上下文策略、幂等键或规范资源 ID，因此不是执行授权。图片、文件和历史消息统一引用候选目录中的 `iN`、`fN`、`mN`；客户端解析显式序号/ID/唯一标签并重建 bindings，由能力注册表统一校验 operation 的资源类型、角色和数量。消息上下文遵循“精确绑定只带所选、明确新任务不带历史、其他默认带窗口内会话”，超限时先丢弃最早普通历史且不生成摘要。最终不可变的 `dispatch_contract.v1` 仍是唯一执行授权；缺失、歧义、不可用、固定模式冲突或跨 API 多任务必须在本地变成澄清合同。

#### 澄清阶段

当 `readiness = needs_clarification` 时：

- 必须展示澄清或选择 UI；
- 不得创建最终聊天 Job；
- 不得创建最终图片 Job；
- 不得调用 `/images/generations` 或 `/images/edits`；
- 原始任务必须保持 pending，用户完成选择后才能继续。

# A. 最小配置

## CFG-CORE-001 服务与模型配置

**测试场景**

验证核心功能所需的 Endpoint、Key 和模型可以保存并生效。

**操作**

1. 访问 `http://127.0.0.1:8765`。
2. 访问 `/api/version` 并记录版本、Git SHA 和 sourceRevision。
3. 打开配置。
4. 设置可用 Endpoint Base URL、API Key、聊天模型 C1、路由模型 T1、图片模型 I1。
5. 保存并刷新。

**预期输出**

- 页面正常显示，无白屏。
- 配置保存成功。
- 刷新后模型和 Endpoint 保持。
- Endpoint 不重复拼接 `/v1/v1`。
- Console 无未解释异常。
- API Key 不出现在 URL、页面正文或 Console。

**通过标准**

聊天、意图识别和生图分别使用对应模型，且页面刷新后配置不丢失。


**预期输出**

- 最终聊天请求为流式请求。

- `dispatchContract.operation = plain_chat`。

- 两个任务可独立停止和恢复。
- 每个结果回写到自己的消息位置。

---

## REC-CORE-005 SSE 断开恢复

**前置条件**

G1 可控制 SSE 断开；否则标记 `SKIP`。

**操作**

1. 启动长聊天。
2. 中途断开 SSE 数秒。
3. 恢复连接。

**预期输出**

- 前端重连或轮询任务。
- 已显示内容不清空。
- 最终结果与服务端 Job 一致。
- 不重复创建上游请求。

---

## REC-CORE-006 停止后刷新不得复活

**操作**

1. 启动长聊天或慢速生图。
2. 点击停止。
3. 刷新并等待 10 秒。

**预期输出**

- 任务保持停止状态。
- 不继续追加文字。
- 不再出现图片。
- 不重新请求上游。

---

## REC-CORE-007 服务重启后的任务状态

**前置条件**

受控重启当前 `8765` ChatUI 服务，不得启动其他端口实例。

**操作**

1. 启动较慢任务。
2. 重启当前服务。
3. 返回原会话。

**预期输出**

如果任务可恢复：

- 恢复原任务和已显示结果。
- 不重复执行。

如果跨进程任务不可恢复：

- 显示明确的“服务已重启，任务不可恢复”或等价错误。
- 不永久 loading。
- 不生成第二个任务。

## PROTO-CORE-009 API Key 不泄漏

**操作**

- 普通服务日志；
- 错误提示；
- 下载文件；
- 路由 prompt；

**预期结果**

当前客户端向本地任务或代理接口传递 Key 属于本地代理边界；验收要求是它只能进入必要的本地受保护请求，不能进入 URL、模型 prompt、页面文本、普通日志或错误信息。

## PROTO-CORE-010 跨会话资源和 Job 隔离

**预期结果**

- A、B 的 Job ID 和结果位置相互独立。
- 不使用全局“最近图片”跨会话回退。

- 连续非法时明确失败。
- 不无限重试。
- 不执行未经验证的图片资源合同。
- 不根据猜测创建图片 Job。

# H. 最终验收标准

以下条件全部满足，才能认为聊天和生图核心功能通过：

## 聊天

- 普通回答真实流式显示。
- 多轮上下文和短句追问连续。
- Enter、Shift+Enter 和中文输入法行为正确。
- 停止后不继续写入，刷新后不复活。
- 编辑重发和重新生成不会破坏消息顺序。
- 会话之间不串消息、Job 或模型状态。

## 意图识别

- 普通聊天、图片问答、OCR、图片比较、文本生图、参考图生成和图片编辑能够区分。
- 新任务不继承无关历史图片。
- 当前图、引用图、历史图和第一张/第二张身份稳定。
- 模式冲突、目标缺失、目标歧义和参数冲突会进入澄清。

## 澄清

- 能选择时优先显示按钮或图片候选。
- 用户完成所有选择前不执行最终请求。
- 非法编号和过期选择不会触发猜测执行。
- 澄清中发起新任务时允许选择继续原任务或开始新任务。

## 生图和修图

- 图片参数与执行计划一致。
- 目标图、参考图、风格图和 mask 角色正确。
- 未选图片不得进入最终请求。
- 生图和修图可以停止、刷新恢复和跨会话隔离。
- 图片预览、下载、复制和历史引用稳定。

## 协议和安全

- 意图识别请求使用 `intent_recognition`，且不携带执行计划。
- 最终执行请求使用 `final_execution`，且携带合法 `dispatch_contract.v1`。
- 澄清状态不创建最终 Job。
- 执行计划、binding evidence、最终 payload 和实际资源一致。
- 路由模型不接收图片二进制。
- 内部控制字段不透传上游。
- API Key 不出现在 URL、页面、模型 prompt、Console 或普通日志中。
