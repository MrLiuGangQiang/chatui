# 25 流式并发、会话隔离与任务续接设计

> 候选 R1，实施前冻结。历史草案未通过且全部废弃；本版尚未实施。评审必须针对本文件 SHA-256，至少三轮三方无阻塞结论后才实施。实现、测试和发布门分别验收，不把未实施当作设计不通过。

## 1. 范围、事实与决策

项目保持无构建、Node 原生 HTTP、现有 JobStore、principal cookie、Job DTO、GET ids/offset 和 image_batch_execution.v1。不改 CORS/身份认证，不引入服务端 session epoch、持久化任务队列或新任务 schema。

已确认根因：128 个 ID 被静默截断；metadata-only 初始事件清空正文；同 Job 多 waiter 独立累加重复；旧 EventSource 迟到回调仍有效；多路 subscriber 未绑定 Job 对象；SSE 忽略背压/缺心跳；托管上游逐 Buffer.toString 可能破坏跨 chunk UTF-8；batch 会话删除漏索引/子快照/父任务。

200 容量必须分别验证：A=200 个独立 HTTP SSE response，每个一个 Job；B=单个浏览器 runtime 内200个不同 session/Job；C=显式 MAX_UPSTREAM_CONCURRENCY=200 时200个合成上游同时运行。默认30 active+100 queue不擅自提高；部署200活跃上游需要明确配置和上游配额。测试不使用真实计费模型。

## 2. 客户端连接与聚合

现有 client/app/job-event-multiplex.js 是 facade/编排；纯传输可移入已加载的 client/services/job-service.js，不能依赖 UI。既有文件可复用，不改根 app.js 业务。

1. 至多4条 Chat EventSource，给 HTTP/1.1 同源连接池的 presence/普通请求留下余量。每条至多64个ID且最终 ASCII URL字节数≤6144。ID升序、URLSearchParams 的 ids 在前、offset=id:contentLength:reasoningLength 依同序追加。稳定first-fit，计入完整path/query。按最坏安全整数offset预留位数，避免输出增长导致URL越界。
2. 常规生成ID的200个Job可放入4条流。更长ID的溢出Job使用GET完整快照轮询，不开启第5条流：每2.5秒一次，全runtime最多4个在途poll，单次5秒超时，轮询连续网络失败60次停止本地follower但保留恢复owner（非任务失败）；成功running重置失败计数。404/服务端error才清理对应owner。流已恢复则停止poll，不能双路同时应用。无poll函数用服务层GET默认实现。
3. 每个jobId一份canonical aggregate、Set<waiter>；首waiter base初始化，后waiter立即收到已有完整状态且忽略自带旧base。abort仅退出该waiter，末waiter退出清除record。后续非空sessionId与已绑定sessionId冲突时只拒绝后waiter，既有record不变；恢复工作流必须传sessionId。传输不能直接清理localStorage，清理由工作流按自己的owner完成。
4. compact d/r只应用一次再分发；任意无data事件是patch，保留正文/思考/metrics；终态优先，不能被running回退。仅full data快照更新正文时使用快照权威值。禁止SSE与GET快照同时写aggregate：切换到poll之前关闭SSE并推进connection epoch；切换回SSE前等待poll完成/取消，再捕获最新offset。所有回调必须匹配epoch，包含event/open/error/poll/timer。
5. 动态新增/退出只重建受影响shard；重建固定为先无效化并close旧source，再捕获canonical offset建立新source，绝不恢复旧source。无事件历史也不会丢：服务端Job aggregate保留全部内容，初始offset回放补齐断开间隙。JSON解析失败立即走同一重连流程，不忽略损坏delta继续拼接。
6. onerror立刻close旧source（阻止浏览器自动重连叠加），应用重试1–5秒、±20% jitter，连续失败8次转poll。只在收到合法Job事件后清空失败计数，单纯onopen不清空。收到terminal只结算该Job，空shard close；pageUnload停止重连；closed manager 的subscribe立即拒绝。
7. offset以JS UTF-16 code unit计量，与String.slice一致；正文/思考独立。建立新连接时不并行poll。初始contentLength/reasoningLength若越过服务器内容长度，服务端发送该Job完整data快照而非只裁剪suffix；客户端据完整快照重置。缺offset默认0，非法数字拒绝。终态的最后suffix必须先交付再结算。

## 3. 服务端事件、背压和回放

在 server/jobs/events.js 组织绑定、公开视图；通用分块writer放 server/http/sse-writer.js，不新增全局浏览器导出。

- 每条response一个subscriber，Map<id,{job,contentOffset,reasoningOffset}>和有界dirty Set；按JobStore对象引用+principal匹配，不能仅按id授权。旧对象notify查到新对象binding时直接忽略，不能误删新binding。dispose/终态/响应close统一摘除所属对象binding，末binding结束writer；server shutdown按唯一subscriber去重。
- 每个binding的已送offset来自已被writer接纳的帧；发送compact正文/思考从权威job.data切suffix，不依赖可能过期/丢失的streamDelta。运行中按25ms合并更新，只保留dirty Job引用，不排队每token事件；初始回放和terminal立即pump。每次最多16帧后setImmediate让出事件循环；pump以轮转顺序避免单长输出饿死其它Job。
- compact每帧正文和reasoning合计最多8192 UTF-16单元（JSON最坏<64KiB）；长回放分多帧，终态仅在该binding的suffix全部接纳后附带。与现有compact d/r/done/e/status合同兼容。非compact Job仍用现有完整DTO，不改变图片/批次data。
- writer一次只持有一帧，串行按≤16KiB块写入；write(false)表示当前块已接纳，进入BLOCKED，不重写该块也不继续write。等待drain再继续；期间新notify只合并dirty引用。10秒无drain则destroy并移除所有bindings。阻塞时不写心跳；永不暂停其它subscriber/上游managed Job。writer结束须先排空已接纳帧，再end；正常close/error/timeout/shutdown都清理timer/listener，端到端一次close。
- 不把write(false)立即destroy当作常规策略：大初始snapshot可因此永远无法恢复。完整非compact帧有独立64MiB上限，超限只断开消费者并交由既有GET恢复，不能宣称无限图片输出支持。
- Job心跳固定15秒注释帧，unref，不更新job.updatedAt；X-Accel-Buffering:no、private/no-store/no-transform保留，部署proxy_buffering off/read_timeout≥60s。shutdown结束全部response、清理writer。CORS保持既有*且不新增Allow-Credentials；内置前端同源Cookie，*本身不授予跨域Cookie读取能力。
- GET组端点严格校验：完整req.url≤6144bytes、ids一次非空，重复ID拒绝；chatjob-后1–80个ASCII字母数字/连字符（兼容短历史ID）；最多64个；offset可缺省，若存在则必须对应ids且不重复、恰3字段、数字匹配0或无前导零十进制且安全整数。无效400，过长414，不静默截断；GET以外405。不存在和非owner同样200 job error，只影响该id。

## 4. 上游完整性与资源边界

- 托管chat runner用StringDecoder贯穿整个上游body与end；parser一次chunk的streamDelta先完成再notify，避免默认notify路径提前广播旧delta；25ms输出合并不改变Job权威文本。
- 直通proxy（若无managed job）下游write(false)停止读取上游等待drain，10秒超时abort上游；managed proxy下游慢/断线只断开下游，继续权威Job并可恢复，不能把页面断线当作用户取消。
- 不把“200任意附件、无限输出”当作容量承诺。输出正文+思考合计默认8MiB/Job、解析未终止SSE event buffer默认1MiB，超限走明确Job error并停止上游；完整输出和保留的terminal继续计入JobStore容量。JobStore默认200，部署200 active另需预留排队/保留终态容量（建议MAX_JOBS_PER_STORE=512）；超额不应驱逐正在服务的老任务：新增Job若无可淘汰terminal，则同步429，保留老Job。
- 本次不引入全局精确RSS reservation（无法代表V8/OS实际开销）；压力测试报告指定小文本负载的RSS/heap/event-loop，必须明确实测环境和负载。大附件输入仍受已有10MiB文件策略/请求body硬上限；这不是200份大附件同时排队的保障，运维必须按实测调低并发。

## 5. 会话隔离与批量删除（现有合同）

安全边界是principal（不是前端会话id）；没有发现绕过owner的可靠证据，不伪造服务端session安全特性。本地工作流固定捕获sessionId、Job id、liveItem/displayItemId/responseIndex、run对象；后台回调写目标session，DOM操作必须activeSessionId匹配，disposed或当前run/owner已替换时不提交旧任务、不清除新任务owner。刷新/切换复用现有single-flight；不更改跨标签页数据模型。

session resource manifest应复用submit-workflow.helpers的imageBatchIndexKey/imageBatchChildKey和读取函数：枚举index.children及storage中该session的child前缀（损坏index也清理），从parentJobId、display.batchJobId/jobId、activeRun image_batch取得父id；保持其它session前缀不动。服务层disposeManagedJob(kind=image_batch)映射已有/api/image-batches/:id，父dispose级联child；清除image_batch:session的resuming状态和本sessionchild following ids。先标记disposed/abort本地run，构造manifest后立即清本地恢复资源；远端最多3次（1s/2s退避、每次5秒）best-effort，离线留给服务端TTL，不声明跨关闭持久清理队列。parent已dispose后child迟到更新必须比较parent在store中的对象引用，不能更新新parent。媒体沿用现有跨session引用计数，不误删其它session文件。

## 6. 实施与测试门

实现文件：现有 client/app/job-event-multiplex.js、job-workflow.js、job-resume-workflow.js、session-resources.js、client/services/job-service.js；server/jobs/events.js、chat-stream-parser.js、chat.js、store.js、image-batch.js、server/http/sse-writer.js、server/proxy/openai.js。尽量不改root静态入口；若增加浏览器脚本则同时处理manifest/static/Docker/测试/架构。

每个根因独立红绿测试（自定义runner，不能直接run suite）；通过npm test自动发现即进入npm run check/CI，不重复跑全套。test:streaming只提供同一runner聚焦别名。所有设计/架构/开发文档同次更新；版本不手改。

固定门禁按三个profile分别验收，不能用一个profile替代另一个：

- **Profile A（接入连接）**：`test/smoke/chat-job-sse-capacity.test.js` 在8765真实HTTP server维护200个独立SSE response，每个response绑定一个synthetic Job；每Job发送20个256-byte正文+64-byte思考update和一个terminal；20个连接模拟write(false)+drain。deadline 60s；200/200 terminal，0 lost/duplicate/pending；测试末subscriber/timer清零；RSS诊断增长≤256MiB；不调用真实上游。
- **Profile B（单浏览器恢复）**：同一模拟browser runtime恢复200个不同session/Job，first-fit至多4条EventSource；溢出Job按设计进入至多4个并发GET polling；动态新增10 Job、切换5 session、断线重连1次；deadline 60s；最终正文/思考与synthetic source逐Job相等，0重复、0跨session写入、0pending。
- **Profile C（上游准入）**：ConcurrencyLimiter fixture以默认30 active/100 queue断言前130个新执行请求按现有active/queue语义，131及以后返回既有429且不留下新Job；另以显式 MAX_UPSTREAM_CONCURRENCY=200 验证200个受控任务可active。只测准入/释放，不调用供应商。
- **Unit/server门**：waiter聚合、UTF-16 offset、status-only、handoff、stale object、write false/drain、keepalive、严格ids/offset、batch清理和terminal一次性；使用fake clock，单项≤10s。
- **运行残留门**：各profile结束时所有shard/subscriber/timer/poll task为0；JobStore仅按测试fixture清理，不驱逐服务中老Job。测试使用端口8765；占用时复用或报告，不换端口。
