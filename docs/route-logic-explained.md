# ChatUI 当前路由逻辑说明

> 本文面向不需要阅读代码的产品、设计和业务人员。
>
> 目标：用普通语言说明 ChatUI 如何判断用户想做什么、应该使用哪张图片或哪个文件，以及为什么有时会要求用户补充信息。

---

## 一、先说结论

ChatUI 的“路由”可以理解成一个**任务分流员**。

它不负责直接回答问题，也不负责直接生成图片。它先回答四个问题：

1. **用户这次真正想做什么？**
2. **用户说的是哪一张图片、哪一个文件或哪一段历史内容？**
3. **现有信息够不够完成？**
4. **应该交给聊天、看图、读文件、生图还是修图？**

完整流程是：

```text
用户输入
  ↓
整理本轮可用的信息
  ↓
判断用户意图
  ↓
核对图片、文件和历史消息
  ↓
信息完整？ ── 否 → 询问用户补充或选择
  │
  是
  ↓
交给聊天 / 看图 / 读文件 / 生图 / 修图
  ↓
保存结果和它对应的历史资源
```

最重要的一点是：**路由模型只负责提出“建议”，最终决定由应用自己核对后做出。**

这样做的目的，是防止模型随意编造图片、文件、接口或执行参数。

---

## 二、用户的一句话会被拆成什么

用户按下发送后，系统不会只看文字，还会同时整理以下信息：

### 1. 本轮文字

例如：

- “画一只猫”
- “这是什么品种”
- “帮我把猫的颜色换一下”
- “总结这个 PDF”
- “根据上面的描述再生成一张”

本轮文字是最重要的信息。

### 2. 本轮上传的内容

例如：

- 本次刚上传的图片；
- 本次刚上传的 PDF、Word、表格等文件；
- 粘贴进来的图片。

这些内容会被标记成“本轮上传”。

### 3. 用户明确引用的内容

例如用户点击某条消息旁边的“引用”，或者选择某张历史图片。

这类内容会被标记成“用户明确指定”，优先级很高。

### 4. 历史内容

包括：

- 以前生成过的图片；
- 以前上传过的图片；
- 以前的文字消息；
- 以前使用过的文件。

历史内容只是“可能有帮助的证据”，不会因为它存在就自动被使用。

### 5. 当前对话焦点

系统还会判断最近对话主要在谈什么：

- **文字**：最近主要是在讨论一段文字、回答或说明；
- **图片**：最近主要是在生成或修改图片；
- **不确定**：文字和图片都可能是用户想继续处理的对象。

这个判断用于防止用户说一句普通话，系统却误把很久以前的图片拿出来修改。

## 三、系统会先列出“现在有哪些东西可以用”

系统会建立一张当前可用内容清单。用户不需要看到这张清单，但它是路由判断的基础。

清单中的每个对象都会有一个很短的临时称呼，例如：

- `i1`：第一个图片候选；
- `i2`：第二个图片候选；
- `f1`：第一个文件候选；
- `m1`：第一条可引用的历史消息。

这些短称呼只用于本次判断，不是图片真正的长期身份。

### 图片清单通常包含

- 它是本轮上传、引用的图片，还是历史图片；
- 图片所在的顺序；
- 图片的简短描述；
- 是否仍然可以恢复使用。

### 文件清单通常包含

- 文件类型；
- 文件名；
- 是否可以读取；
- 它是本轮上传还是历史文件。

### 路由模型看不到什么

为了节省上下文，也为了安全，路由模型不会收到：

- 图片本身；
- 图片的 Base64 内容；
- 文件正文；
- 图片或文件的长期存储编号；
- 一大串只用于区分资源的内部编号。

路由模型只看“这是什么、来自哪里、能不能用”的简短说明。

路由模型会看到当前消息之前、在受控窗口内能够容纳的文字历史；当前正在发送的消息不会重复进入历史。所有正常会话和引用/澄清 override 都经过同一个 `route_context_policy.v1`：超过窗口时按完整旧轮次丢弃普通历史，不生成“历史摘要”，也不改写当前输入或显式引用原文；如果这些受保护内容本身装不下，系统会在请求模型前明确失败。图片和文件正文仍不会发送，视觉执行状态只保留必要的紧凑事实。

对于“性能方面呢”这类简短追问，系统会先得到完整目标，例如“继续说明 Java 和 Python 在性能方面的差异”。真正交给回答模型时，只保留这个完整目标；不会再重复附带“性能方面呢”这句原话，避免浪费上下文。

## 四、路由模型到底要判断什么

路由模型需要完成三类判断：

### 1. 判断任务类型

目前主要有这些类型：

| 用户想做的事 | 例子 | 后续去向 |
|---|---|---|
| 普通聊天 | “你好”“帮我解释一下” | 聊天回答 |
| 读文件 | “总结这个 PDF” | 文件问答 |
| 看图片 | “这是什么品种” | 图片问答 |
| 比较图片 | “比较这两张图的区别” | 图片比较 |
| 识别图片文字 | “把这张图里的字提取出来” | 图片文字识别 |
| 生成新图 | “画一只猫” | 图片生成 |
| 参考图片生成 | “参考这两张图做一张海报” | 参考图片生成 |
| 修改现有图片 | “把背景换成雪山” | 图片编辑 |

### 2. 判断用户和上一轮的关系

| 关系 | 说明 | 例子 |
|---|---|---|
| 新请求 | 本轮输入和 current 附件即可完成 | “帮我写一封邮件” |
| 追问 | 依赖引用、历史资源或省略上下文 | “那它是什么品种？”“第一条”“为什么？” |
| 纠正 | 认为上一轮结果不对，要求修改 | “不对，把颜色改成黑色” |
| 继续执行 | 明确要求继续或重做上一项任务 | “继续使用这张图，再生成一个夜间版本” |

`correction > continuation > followup > new`。使用 quoted/history/context 资源时属于 `followup`；只用 current 附件仍可以是 `new`。参考生成中，主体/内容/构图使用 `reference`，画风/配色/质感使用 `style_reference`；修改图片本身才使用 `edit_image/target`。

### 3. 说明真实目标并选择精确资源

路由模型只返回 `route_intent.v2` 的五个字段：任务类型 `operation`、关系 `relation`、消解目标 `goal`、资源选择 `resource_refs` 和任务形态 `task_shape`。`goal` 只消解“这个呢”“第一条”“为什么”等指代并合并用户已经提出的约束，不会擅自补充场景、风格、构图或颜色。`task_shape=multi` 表示多个独立任务：图片任务交给二级规划，其他任务要求拆分。模型不会直接决定长期资源编号，只会选择清单中的短称呼，例如图片 `i1`、文件 `f1` 或历史消息 `m1`；历史消息同样作为普通资源绑定。 每次请求的严格 schema 会把 `candidate_key` 限制为本轮实际展示的短称呼；若没有候选资源，模型在结构上就不能返回资源引用。对无历史状态的当前请求、精确连续编辑锚点和明确的只读继续关系，程序只在请求前收窄允许值，不会在模型返回后偷偷修正结果。

最终执行上下文按三条规则选择：能明确定位一条或多条消息时，只携带这些消息；能明确判断为独立新任务时，不携带历史；其他情况默认携带窗口内会话。若超过模型窗口，先丢弃最早的普通历史，不自动生成摘要；当前消息和精确绑定消息不能被丢弃，无法容纳时直接停止发送。引用消息会与最近任务共同参与意图分析，例如最近问题是“这个消息多少字”，引用另一条消息后问“这个呢”，`goal` 应解析为“统计当前引用消息的字数”。

## 五、模型给出建议后，应用还要再检查一次

这是当前设计中很重要的一层。

模型说“这是修图”，应用不会立即执行，而是继续核对：

### 1. 这个对象真的存在吗

如果模型选择了 `i1`，应用会检查 `i1` 是否真的在当前清单中。

不存在的对象不能执行。

### 2. 对象真的适合这个任务吗

例如：

- 修改图片必须有一张目标图片；
- 读文件必须有可读文件；
- 比较图片通常需要两张图片；
- 新生成图片不应该偷偷绑定旧图片作为编辑目标。

### 3. 用户有没有明确指定对象

如果用户说：

- “第一张图”；
- “第二个文件”；
- “左边那张”；
- “把猫改成黑色”；

应用会优先按照用户明确说的内容检查，而不是盲目听从模型的猜测。

### 4. 是否存在多个可能对象

例如历史里有两张猫图，用户只说：

> 把猫的颜色换一下

系统无法安全确定是哪一张，就应该让用户选择，而不是随便挑一张。

### 5. 当前文字是否已经改变了主题

例如最近用户一直在讨论一段 Markdown，随后只说：

> 再复杂一点

这句话可能是说文字，也可能是说图片。系统应该先询问，而不是直接修改很久以前的图片。

但是如果用户说：

> 帮我把猫的颜色换一下

并且历史中只有一张明确描述为“猫”的图片，那么这属于具体的图片修改，应该继续使用那张历史猫图。

## 六、当前截图中的猫为什么应该继续使用历史图片

这段对话可以这样理解：

```text
用户：画一只猫
系统：生成猫图
用户：这是什么品种
系统：回答猫的品种
用户：帮我把猫的颜色换一下
```

第三句回答虽然是文字，但最后一句又明确出现了：

- “把……换一下”：说明要修改；
- “颜色”：说明修改的是图片视觉效果；
- “猫”：说明目标主体；
- 历史里恰好有一张猫图。

因此正确处理应该是：

```text
找到历史猫图
  ↓
把它当作本次修改目标
  ↓
进入图片编辑
```

而不是：

```text
要求用户重新上传猫图
```

只有在以下情况，才应该要求用户补充：

- 历史猫图已经无法恢复；
- 历史中有多张都可能是猫图；
- 用户没有说清楚具体要改什么；
- 用户说的是普通问题，而不是修改请求。

## 七、什么时候系统会向用户提问

系统提问不是失败，而是为了避免误操作。

### 情况一：缺少目标

用户说：

> 把背景改成雪山

但历史里没有图片，也没有本轮上传图片。

系统应该问：

> 请提供或选择要修改的图片。

### 情况二：有多个候选

用户说：

> 把刚才那张图改成黑白

但最近有三张图片都可能是“刚才那张”。

系统应该显示候选，让用户选择。

### 情况三：修改内容太模糊

用户说：

> 再精致一点

这句话没有说明要改什么，系统应该问：

> 你想调整主体、背景、构图，还是颜色和材质？

### 情况四：用户回答了部分问题

例如系统问“要处理文字还是图片”，用户选择了“图片”，但还没说明图片要怎么改。

系统会保存这个选择，下一次只继续询问缺少的部分，不会把前面的信息丢掉。

## 八、图片、文件和文字各自怎么走

### 1. 普通文字

```text
用户问题
  ↓
判断为普通聊天
  ↓
交给聊天模型
```

### 2. 文件问题

```text
用户上传或选择文件
  ↓
判断为读文件
  ↓
把文件交给聊天模型读取
```

文件不会进入图片生成流程。

### 3. 生成提示词，不等于生成图片

例如：

```text
换一个场景，帮我生成提示词
```

这句话是在要一段文字，不是在要系统立即画图。系统会按普通对话处理，返回新的生图提示词；即使上一轮刚生成过图片，也不会因此启动生图。

只有用户明确说“基于这个提示词生成图片”“画出来”之类的话，才会真正进入生成图片步骤。

### 4. 新生成图片

```text
“画一只猫”
  ↓
没有目标图片
  ↓
生成新图片
```

### 5. 修改现有图片

```text
“把背景改成雪山”
  ↓
找到目标图片
  ↓
把目标图片交给图片编辑服务
```

### 6. 参考图片生成

```text
“参考这两张图做一张海报”
  ↓
找到两张参考图
  ↓
生成一张新图
```

这里的参考图只是参考，不等同于要直接修改其中某一张。

## 九、历史图片是怎么被保留下来的

每次图片生成或修改完成后，系统会同时保存两件事：

1. 图片本身的本地存储位置；
2. 这张图片对应的描述、来源和所属对话。

下一次用户说“上一张图”“刚才那只猫”或“把它改成黑色”时，系统可以从历史中找到对应图片，再恢复使用。

发送给路由模型的是短称呼，例如 `i1`；真正恢复图片时，应用在本地完成对应关系，不需要把长编号交给模型。

### 这次新增的“图片记忆卡”

现在系统会为历史图片保留一张简短的记忆卡，内容包括：

- 这张图的清楚描述，例如“橘猫坐在窗边”；
- 主要标签，例如“橘猫、窗边、雪山”；
- 它来自哪一次生成或上传；
- 它是否由另一张图修改而来。

即使这张图已经不在最近几张图片里，只要用户说出了足以区分它的特征，例如“前面窗边的橘猫”，系统仍会先在本地完整历史中找到它。除了语义描述，记忆卡还保存生成轮次、倒序轮次、组内序号和全局图片序号，因此“第八次生成的图”“倒数第二次生成的图”“历史第 12 张”“很早之前那张”都走结构化定位，而不是靠关键词碰运气。

但系统不会把所有旧图片都交给模型。当前/引用资源优先，然后只发布命中的结构化候选、很早历史的有界切片或语义相关候选，并继续使用短称呼。目录发生截断时，`resource_catalog.v1` 会告诉模型历史总量、实际发布量和使用的检索策略，避免把“没发布”误解成“历史里不存在”。

对于连续修改，系统还会保留“它从哪一张图改来”的关系，为以后理解“上一版”“改背景之前那版”打下基础。

### 文字夹在中间，也不能忘记已经找准的图片

例如先生成过一张美女图片，后来又聊过几句提示词：

```text
美女图片我需要全身图
```

这句话虽然没有写“把这张图片改成”，但“美女图片”和“全身图”已经说明了：用户想把那张美女图改成全身构图。

如果历史里只有一张明显匹配的美女图，系统会直接选中它并进入图片修改；如果有两张以上都像，系统会展示候选让用户选择；如果用户明确说“生成一张美女全身图”，则会新生成，不会改旧图。

### 执行前和结果中的可见提示

当系统准备修改历史图片时，聊天中会显示一张小卡片：

- 要使用哪张图片的小预览；
- 它的简短说明；
- 这次准备怎么修改。

这张卡片会在处理时显示，并保留在最终结果旁边。这样用户可以看见系统是否选中了正确的图片，而不是只能相信系统“自己知道”。

这不会把小预览当成一张新图片保存，也不会让它干扰后续的历史判断。

当确实需要用户选择时，图片本体和整张候选卡都是“选择”动作，右上角预览按钮只负责放大查看，不会偷偷改变选择。每组会显示“编辑目标 / 内容参考 / 风格参考 / 蒙版”等角色、当前槽位进度、图片来源和精简标签；桌面、窄屏和手机分别以 3、2、1 列展示，避免把竖图裁成难以辨认的横条。

## 十、当前实现中比较合理的地方

### 1. 当前输入优先

用户本轮说的话不会被旧历史随意覆盖。

### 2. 模型只提建议，应用负责核对

这比让模型直接决定“调用哪个服务、使用哪张图”更安全。

### 3. 不确定时会询问

多张图片、缺少文件、目标不清楚时，不会随便执行。

### 4. 历史图片可以继续使用

只要历史图片仍然存在且能唯一确定，就不应该要求重新上传。

### 5. 路由模型看到的是压缩后的信息

图片内容和文件正文不会送给路由模型；只发送必要的简短描述。

### 6. 生图和修图被分开

“画一张新图”和“修改一张旧图”不是同一件事，系统会区分处理，避免把旧图误当成新图的修改目标。

## 十一、当前实现仍然值得评估的地方

下面这些不是已经确认的错误，而是评估时应该重点关注的地方。

### 1. 判断信息是否有重复

现在系统会同时保留几类“上一张图片”的说明：

- 最近生成的图片；
- 最近使用的图片；
- 上一次图片任务；
- 当前对话焦点。

它们各自有作用，但部分内容可能重复。长期来看，可以考虑把它们整理成一个更简单的“当前图片状态”，减少相互冲突的可能。

### 2. “主体匹配”是否足够准确

例如用户说“把猫的颜色换一下”，系统靠“猫”匹配历史图片。

这对简单场景有效，但如果历史里有：

- 一张猫图；
- 一张猫和狗的合成图；
- 一张描述中也提到猫的风景图；

就需要更严格的选择规则，不能只看一个词。

### 3. 普通文字回答之后的图片延续

当前逻辑已经支持“先问图片问题，再继续改图”，但这是最容易出现误判的场景。

建议重点测试：

- 图片 → 图片问答 → 修改图片；
- 图片 → 普通文字讨论 → 修改图片；
- 图片 → 多张图片比较 → 修改其中一张；
- 多张相同主题图片 → 修改其中一张。

### 4. 模糊表达是否会让用户觉得麻烦

系统为了安全会询问，但询问太多会让体验变差。

需要平衡：

- 一张图片且目标明确时，直接执行；
- 多张图片时，明确展示选择；
- 只有真正无法判断时才提问。

### 5. 负责判断的服务暂时不可用时

服务故障和业务信息不足不是一回事。未配置、鉴权失败、限流、网络/上游错误、超时、非法模型输出或请求次数达到上限都会显示为明确失败，不会伪装成“请再补充一点”，也不会用本地关键词偷偷替模型决定聊天、生图或修图。只有模型成功给出合法意图、但确实缺少业务资源或参数时，系统才建立 pending 澄清。

primary、fallback、图片规划和协议兼容请求共享同一个任务级账本。每一次真实 HTTP 请求都计数，澄清后的下一轮继续沿用该账本；达到 6 次后，第 7 次会在发送前被阻止。这样限制的是实际网络放大，而不是看起来只有一次、底层却重试多次的“逻辑调用”。

用户看到的等待状态也只描述任务进展：多图规划显示“正在拆分多个图片任务”，切换 fallback 时显示“正在重新确认任务意图”，不会暴露内部供应商故障措辞或隐藏推理过程。

## 十二、建议的验收标准

不需要看代码，只要用下面这些对话测试即可。

### 普通聊天

```text
你好
帮我解释一下什么是递归
```

预期：只回答文字，不调用图片服务。

### 新生成图片

```text
画一只猫
```

预期：生成一张新图片。

### 历史图片修改

```text
画一只猫
这是什么品种
帮我把猫的颜色换一下
```

预期：直接使用历史猫图进行修改，不要求重新上传。

### 多张图片选择

```text
连续生成两张猫图
把猫的颜色换一下
```

预期：如果无法唯一确定，显示图片选择，而不是随便修改一张。

### 很久以前的历史图片

```text
先后生成很多张不同图片
……
把前面窗边的橘猫背景改成雪山
```

预期：系统能从完整历史中找回“窗边的橘猫”；不会把全部旧图都带去判断，也不会误改最近一张无关图片。

同时，处理中的消息和最终结果旁应显示：

```text
将修改这张图片：橘猫坐在窗边
修改内容：把背景改成雪山
```

并显示对应的小预览图。

### 文件问答

```text
上传一个 PDF
总结一下这份文件
```

预期：读取 PDF，不进入图片编辑或生图流程。

### 明确引用文字生成图片

```text
上一条描述了一只橘色的猫
根据上面的描述画一张图片
```

预期：使用文字描述作为参考，生成新图片，但不把文字消息当成图片。

### 模糊图片延续

```text
画一张海报
再精致一点
```

预期：如果“精致”没有明确修改对象，系统询问用户想调整哪里。

### 不存在目标图片

```text
把背景改成雪山
```

预期：没有可用图片时，提示用户上传或选择图片。

## 十三、对当前实现的总体判断

当前路线整体是合理的，而且现在已经具备“能延续上下文、但不乱猜”的基础。核心思路是：

```text
模型帮助理解
应用负责核对
不确定就询问
确认后才执行
```

这比“不受窗口和绑定规则控制地把全部历史交给模型，让模型自己猜”更可靠。

换成用户能感受到的话：系统应该记得刚才的猫图；只要能确定你说的就是它，就直接改；如果前面有两张都可能是目标，就请你点选；没有图片就请你提供图片。现在的实现已经按这个原则处理正常情况；服务、配置或协议失败则明确停止，不用猜测性本地路由继续执行。

目前最值得继续优化的，不是再增加更多判断规则，而是：

1. 继续减少重复的历史图片说明；
2. 让图片候选的描述更准确；
3. 让多张相似图片的选择更清楚；
4. 减少本来可以唯一确定时的重复提问；
5. 继续保证路由模型只看到短称呼和必要说明。

对于你截图中的场景，合理结果应该是：**历史猫图被识别为唯一目标，直接进入图片修改，而不是要求重新上传。**
