# 11 意图识别最小决策链设计

## 1. 范围与目标

本设计收敛 ChatUI 的默认意图识别链路，目标是降低对意图模型的额外要求、减少串行模型调用，并避免理解节点、关键词规则、critic 和 repair 多重裁决导致的语义漂移。

适用范围：普通聊天、单图片问答、单文件问答、明确缺失输入的业务澄清，以及明确表达的多任务请求。不改变最终 `dispatch_contract.v1` 的授权边界，不改变图片、文件和聊天执行器的能力集合。

非目标：不在本设计中重新设计 provider API、附件编码、图片生成器或历史持久化格式；不展示模型原始思维链。

## 2. 设计原则

1. 默认请求只有一个语义权威：`route_intent.v3`。
2. 本地代码只做输入完整性、协议结构、资源身份和执行安全校验，不重新猜测用户 operation。
3. 单个当前图片/文件作为回答依据不是独立任务；“根据图片输出测试方案”必须是一个 `image_qa` 单任务。
4. 缺失正文、缺失附件和不可用引用在模型调用前或统一编译阶段产生业务澄清，不伪装成另一个资源类型。
5. `intent_critic`、`semantic_intent`、默认 `route_repair`、默认 fallback 和 `image_planning` 不进入普通单任务请求链路。
6. 明确多任务时才进入任务规划；内部证据读取步骤不得被拆成用户任务。

## 3. 流程与状态

### 3.1 默认路径

```text
captured
  -> input_preflight
      -> business_clarification (missing source)
      -> route_intent
          -> route_validated
              -> ready
              -> business_clarification (missing/ambiguous resource)
              -> invalid_model_output
          -> transient_error / configuration_error / cancelled
```

普通单任务最多调用一次意图模型。结构化输出解析失败时允许一次同协议结构修复；修复仍失败则结束为 `invalid_model_output`，不得转入关键词 fallback。

### 3.2 多任务路径

只有 route 模型明确返回 `task_shape=multi` 且当前输入确实包含多个独立用户动作时，才进入 `multi_task_planning`。图片多结果规划仅适用于明确要求多个独立图片结果的请求。

### 3.3 单资源证据

```text
current_input: 根据上传图片输出测试方案
resource_candidates: i1=image/current
=> route_intent: image_qa + single + i1/source
```

“读取图片”是 `image_qa` 的证据使用，不是另一个 `image_read` 用户任务。

## 4. 协议与模块契约

### 4.1 route_intent.v3

route 模型继续输出现有六字段：

```json
{
  "operation": "image_qa",
  "relation": "new",
  "goal": "根据当前上传图片输出完整测试方案",
  "goal_mode": "replace",
  "resource_refs": [{"candidate_key":"i1","role":"source"}],
  "task_shape": "single"
}
```

单任务请求的 operation、goal、资源角色和 task shape 由同一 route 结果共同表达；所有节点均遵守当前输入（含当前附件）> quoted > understanding/context，理解结果只辅助消歧；本地不得把一个合法 route 改写成另一个 operation。

### 4.2 输入完整性

本地允许识别明确的未兑现 source 指代，例如“下面这段话”“以下内容”，但只判断 source 是否存在：当前正文、quoted/history 消息或文件候选。缺失时产生 `missing_source_text` 业务澄清，不调用意图模型。

### 4.2a 显式联网查找指令

`shared/capability-registry.js` 的 `web_search` 显式指令是本地确定性事实，在编译模型路由时做最小调和：当 `current_input` 命中明确在线查找表述（“查查最新信息”“最近有什么新闻”“check the latest news”）时，模型提案不得把 operation 降级为 `plain_chat`；goal、relation、资源与 task shape 仍由模型决定。指向本地文件/图片的同类句式（“查一下最新的文档”“看看最新生成的图”）不命中该指令。`shared/intent-claims.js` 同步发布 `web_search_request` 声明，仅作为模型证据。

### 4.3 模型调用预算

- 普通单任务：1 次 `intent_recognition`。
- 结构化输出无效：最多 1 次同协议 repair。
- `intent_critic`：仅离线评估或显式高风险实验，不进入默认用户请求链路；若启用，仍只审查 current_input 覆盖情况，不能让 understanding 覆盖当前输入或 quoted。
- `image_planning`：仅明确多独立图片结果且 route shape 已确认时调用。
- 不得用本地关键词路由替代无效模型输出。
- 预算耗尽（`model_calls_exceeded`）是该任务路由阶段的终态失败，不是瞬时条件：失败后存储的澄清状态（`session.pendingClarification.routeInfo`）不得继续携带已消耗的 provider-attempt ledger，下一次重试以全新预算开始；否则重试会继承已耗尽计数器并再次失败。

### 4.4 提示词正反示例与长度门禁

各节点提示词（`client/services/route-prompts.js`）在规则之后内嵌典型正反示例，用于消解最高频的语义歧义：

- 三份路由节点提示词（FULL/SIMPLE/COMPACT）均含 relation 正反示例：修改既有图→`followup+edit_image`，延续连接词+生成动词且无目标图→`continuation+text_to_image`，无历史依赖→`new`；FULL 另含 `goal_mode` 示例（完整新任务→`replace`，只改前序部分约束→`amend`）。
- `INTENT_CRITIC_SYSTEM_PROMPT` 含 accept/repair 示例与合法组合（`image_reference_gen+replace`）不被判为冲突的反例；`ROUTE_REPAIR_SYSTEM_PROMPT` 含只改 `changed_fields` 声明字段、其余字段与 `base_route_intent` 完全一致的示例；`MULTI_TASK_PLAN_SYSTEM_PROMPT` 含拆分文件任务与生图任务、不合并不降级的示例。

长度门禁：UNDERSTAND ≤2600，SIMPLE ≤4000，FULL/COMPACT ≤6400（含正反示例）。COMPACT 与 FULL 共享完整规则集：理解节点只补充动作/指代/依赖证据，不裁决 operation 边界、资源角色、relation 语义、goal_mode 与澄清策略；实测证明精简 CoT 提示词会丢失这些规则并导致误路由（合并→edit、风格参考→reference、询问→continuation），因此复杂路径必须携带完整决策集。长度断言集中在 `test/unit/route-prompts-module.test.js` 及各契约测试中。

## 5. 安全与失败处理

- 所有资源 key 必须来自本轮发布的候选目录；未知 key fail closed。
- `plain_chat` 不得绑定图片或文件；`image_qa` 不得绑定文件；`file_qa` 不得绑定图片。
- 模型输出协议无效、语义无法确认或修复失败时，返回 `invalid_model_output`，不改成澄清，不执行。
- 网络、超时和上游 5xx 返回 `transient_error`；配置缺失返回 `configuration_error`；用户停止返回 `cancelled`。
- 用户可见消息保持简单、可操作；内部 reason code 只写日志和测试。
- 等待态只使用一个 live surface；阶段更新原位替换或追加到当前任务，不创建重复 assistant 节点。

## 6. 验收标准

1. 单张图片加“根据图片输出测试方案”只调用一次 route model，不调用 understanding、critic 或 image planning。
2. 单文件加总结只调用一次 route model并绑定 `fN/attachment`。
3. “总结下面这段话”没有正文、引用或文件时不调用模型，直接显示补充文本澄清。
4. “查查最新信息”等明确在线查找即使模型输出 plain_chat，最终执行仍为 `web_search`；“查一下最新的文档”不被强制成 web_search。
5. 明确“分别执行两个独立动作”时仍能进入多任务规划。
6. route 模型输出无效时不触发本地关键词 fallback。
7. 所有执行都经过 `dispatch_contract.v1`。
8. 默认 Prompt 保持短小，route Prompt 与 understanding Prompt 均通过长度门禁（FULL/COMPACT ≤6400，SIMPLE ≤4000，UNDERSTAND ≤2600），复杂路径与完整版共享同一规则集，并内嵌典型正反示例与决策顺序。
9. 一个 assistant 任务只有一个 reasoning/waiting surface，计时更新不产生重复行或重复操作按钮。

## 7. 回归测试

新增或调整以下测试：

- 单图片证据问答保持 `image_qa/single`；
- 单文件证据问答保持 `file_qa/single`；
- 缺失 source text 在模型调用前澄清；
- 显式联网查找指令在模型输出 plain_chat 时仍调和为 web_search，本地文件/图片句式不被误判；
- 普通单任务调用预算为一次 route 请求；
- critic、fallback、image planning 不进入普通单任务；
- 明确独立多任务仍进入规划；
- route 输出无效时 fail closed；
- 预算耗尽失败后，存储的澄清状态不再携带已消耗 ledger，重试以全新预算开始（`testBudgetExhaustedFailureClearsStoredLedgerForRetry`）；
- reasoning/waiting surface 与操作按钮不会重复创建。

## 8. 实施边界

实现应优先修改 `client/app/route-intent-workflow.js`、`client/services/route-service.js`、`client/services/route-prompts.js` 和必要的共享协议测试。不得通过根 `app.js` 增加新的业务语义判断；涉及 root static entry 的缓存版本必须同步更新静态入口、测试和文档。
