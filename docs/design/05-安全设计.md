# 05 安全设计

## 1. 身份与任务归属

- `request-principal` 为每个浏览器颁发 HMAC 签名 principal cookie：HttpOnly、SameSite=Strict、可选 Secure、可轮换。presence 在线人数按 principal owner key 去重（同一浏览器多标签页计 1）；多实例共享去重时必须为所有实例配置相同的 `CHATUI_PRINCIPAL_SECRET`。
- principal 派生 owner key，chat/image/image-batch 任务按 owner 隔离；非本人任务与不存在任务同样返回 404，避免泄露存在性。
- 颁发/刷新 cookie 的响应强制 `private, no-store`；已持有 cookie 的请求不覆盖业务缓存语义。

## 2. 代理与 URL 策略

- 上游转发只允许白名单方法与路径；重定向与目标 URL 经 `server/security/url-policy.js` 校验，禁止 SSRF 与任意内部地址。
- 代理请求头经 `server/proxy/headers.js` 处理，不把宿主头或不受信头透传给上游。
- 所有服务端出站上游请求（代理、chat/image Job、图片下载、插件 HTTP/MCP、用量校验、反馈审核与投递）在 `server/proxy/headers.js` 统一追加 `User-Agent: chatui/<version>`；版本取自唯一版本来源 `version.json`，调用方已显式设置的 `User-Agent` 不被覆盖。该头不含凭据、不含用户内容，可进入日志。

## 3. 内容安全（浏览器渲染）

- 所有 Markdown 输出必须经 DOMPurify + 消毒策略 + 链接策略；源规范化、mermaid 规范化在渲染前执行。
- 运行期公告目录由服务端只读扫描，`/data/` 不进入静态公开路径；单个 Markdown 文件有大小上限，正文不得包含凭据。同一目录中的推荐模型 JSON 也不得包含 API Key 或连接串，字段按长度上限规范化。公告 SSE 公开只读且 `no-store`，只推送公告快照，不携带 principal、用户数据、内部路径或其他运行期状态。
- CSP 默认 `default-src 'self'`，脚本只允许 self/受信 CDN/inline/blob，样式与字体同策略；图片与连接按需放宽。
- 上传附件按文件类型、大小、数量限制（`shared/file-inputs.js`），上传与展示路径使用受限 URL。

## 4. 密钥与配置

- 私密配置放根目录 `.env.local`（Git 忽略）：只补缺，不覆盖部署环境变量；禁止强制提交。
- 主要密钥：`CHATUI_PRINCIPAL_SECRET`、数据库连接、DingTalk 反馈凭据。所有敏感值只从环境读取。
- `config/public.json` 只放非敏感 UI/feature 配置；服务端数据、SQL、凭据禁止进入静态公开目录或 `shared/`。

## 5. 日志与脱敏

- API Key、Authorization、自定义敏感 Header、文件/图片 Base64、签名 URL 查询参数不写入日志。
- 系统提示词只记录长度与哈希；reasoning 只记录长度；业务正文如需追踪受控落盘，且禁止提交 Git 或附到 Release。
- 意图可见轨迹只允许结构化阶段摘要、证据标识和稳定 reason code；不得展示或持久化原始私有思维链、完整模型输出、凭据或二进制内容。
- 日志 writer 有界异步：队列达到上限显式 drop，不阻塞请求、不无限占内存。
- 错误日志保留受控的 `source`、`stage`、`trace_id` 与错误对象中的 `code`/`statusCode`，用于定位校验阶段；不重复把错误字段塞进上下文，也不将原始诊断写入用户气泡。

## 6. 输入校验

- 路由、幂等、能力契约由 `server/validators/` 集中校验；handler 内不得复制校验逻辑。
- 请求体大小与心跳 payload 大小有上限，超限返回 4xx。

## 7. 上线安全评审清单

- [ ] 无硬编码密钥、无 `.env`/日志提交
- [ ] 新端点有 principal 归属或明确的公开性判断
- [ ] 新渲染路径过消毒与链接策略
- [ ] 新上游路径进白名单且有 URL 校验
- [ ] 敏感字段已脱敏并有回归测试

## 8. 插件出站安全

HTTP 与 MCP 插件配置只存在于服务端运行时文件或环境变量，默认 `data/plugins.json` 且不入 Git。出站请求必须通过 HTTPS/公网校验、逐跳重定向校验、结果大小上限和工具 Schema 校验；凭据只进入上游 Authorization 头。非 GET 默认视为写操作并禁止模型自动调用，只有管理员显式配置 `requiresApproval=false` 才可自动执行。插件结果只是 `role=tool` 数据，不得提升为系统指令；最终渲染仍走既有 Markdown 消毒。

## 9. 入站 MCP 安全

- `/api/mcp` 的 MCP token 就是用户 API Key，只接受 `Authorization: Bearer <API Key>` 或 `X-API-Key` 请求头；query string、JSON-RPC params、客户端自报用户名和隐式回退值均不得用于认证。请求头 token 长度有硬上限，且不会出现在响应、access log、error log 或 request trace 中。
- `initialize`、`notifications/initialized`、`ping`、`tools/list` 和 `tools/call` 每次 HTTP 请求都必须重新通过 `api_keys` 查询与上游 `/models` 校验。校验缓存只保存基于完整 Key 计算的有界哈希结果，不在日志或公开配置中保存原始 Key；上游或数据库不可用时失败关闭并返回可重试说明。
- MCP 不签发 session、不依赖 principal Cookie，也不接受 GET SSE 或 DELETE 清理；认证失败时响应附带 Bearer challenge，服务端排空未读请求体以保持 keep-alive 连接一致。
- 所有 MCP 工具参数按 `server/mcp/contract.js` 的冻结 Schema 校验，未知字段和越界值失败关闭。MCP 部门工具只依赖 API Key，不接收也不校验 `department_password`；浏览器部门接口的密码校验保持不变。导出资源设 8 MiB 上限，超限不返回截断文件。
- 统计与部门工具沿用服务端限流桶，反馈和部门查询使用更严格的 MCP 独立桶；响应固定 `Cache-Control: no-store`，使用 `Access-Control-Allow-Origin: *` 仅为支持无 Cookie 的浏览器型 MCP 客户端，不启用 credentials。
- 反馈审核先于反馈用户名解析和 DingTalk 投递；审核拒绝或审核服务不可用时不得产生外部发送。`CHATUI_MCP_FEEDBACK_MODEL` 是可选的服务端默认审核模型，仅在用户 Key 的可用模型列表中命中时使用，不能绕过模型可用性或工具 Schema。
- MCP 回归必须验证：仅 header token 可认证、`X-API-Key` 可用、body/query token 被拒绝、MCP 部门工具不接受 `department_password`、错误与工具结果不含 token/反馈正文/导出 base64、CORS 与 `no-store` 存在，以及 `/api/mcp` 不会落入通用代理。
