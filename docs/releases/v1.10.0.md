# ChatUI v1.10.0

本版本重构了附件处理链路：新上传的非图片附件不再由浏览器或服务端本地解析，而是通过 OpenAI Responses API 原生 `input_file.file_data` 发送给上游模型。这样可以减少本地解析差异、删除不再需要的解析依赖，并让支持的文档类型由上游模型直接处理。

## 重点更新

### 原生文件输入

- 非图片附件在浏览器中保留为原始文件 Blob，发送请求时才编码为 Base64 Data URL。
- 文件直接进入 `/v1/responses` 的 `input_file.file_data`，不再调用 `/v1/files`，也不再经过 Chat Completions 的文本拼接路径。
- PDF 附件支持 `auto`、`low`、`high` 三档 `detail`；其他文件不会错误地携带 PDF 专用参数。
- 支持一次发送多个文件；服务端会校验 Data URL、媒体类型、Base64 格式、解码后大小和请求体大小。
- 文件正文不写入聊天历史；原始 Blob 通过 IndexedDB 保存，恢复或再次发送时重新编码。
- 任务交给上游后会从服务端内存 Job 快照中移除 `file_data`，减少敏感内容和大请求体的驻留时间。

### 现在支持的文件格式

下面是 ChatUI 当前的上传白名单。文件最终能否被读取，仍取决于所配置的上游是否实现 Responses API 的 `input_file.file_data`，以及所选模型的文件理解能力。

#### 图片附件

- 常见扩展名：`.png`、`.jpg`、`.jpeg`、`.gif`、`.webp`、`.bmp`、`.svg`。
- 带有 `image/*` MIME 类型的图片会进入图片附件链路。
- JPEG、PNG、WebP 会尽量压缩；BMP 会在浏览器支持时转换为 PNG。
- 图片继续使用多模态 `input_image` / 图片编辑链路，不占用文档 `input_file` 路径。

#### PDF、表格、文档和演示文稿

| 类别 | 支持的扩展名 |
| --- | --- |
| PDF | `.pdf` |
| 表格 | `.xla`、`.xlb`、`.xlc`、`.xlm`、`.xls`、`.xlsx`、`.xlt`、`.xlw`、`.csv`、`.tsv`、`.iif`、`.numbers` |
| 文档/富文档 | `.doc`、`.docx`、`.dot`、`.odt`、`.rtf`、`.pages` |
| 演示文稿 | `.pot`、`.ppa`、`.pps`、`.ppt`、`.pptx`、`.pwz`、`.wiz`、`.key` |

#### 文本和代码文件

以下扩展名均会作为原始文件发送，不会在本地读取正文：

```text
.asm .bat .c .cc .conf .cpp .css .cxx .def .dic .eml .h .hh .htm .html
.ics .ifb .in .js .json .ksh .list .log .markdown .md .mht .mhtml .mime .mjs
.nws .pl .py .rst .s .sql .srt .text .txt .vcf .vtt .xml .ts .tsx .jsx
.java .go .rs .php .rb .sh .bash .zsh .tex .cs .scala .kt .kts .swift .lua
.r .jl .ex .exs .erl .hrl .hs .clj .groovy .dart .awk .hbs .mustache .ejs
.jinja .jinja2 .liquid .erb .twig .pug .jade .cmake .gradle .ini .properties
.proto .scss .sass .less .hcl .tf .toml .graphql .gql .ndjson .json5 .yaml
.yml .astro .diff .patch .dockerfile
```

文件名为 `Dockerfile`（没有扩展名）也会被识别为文本/代码文件。除扩展名外，浏览器提供的常见文本、代码、Office、表格和演示文稿 MIME 类型也会参与识别；当扩展名和 MIME 类型不一致时，客户端会按文件名推断安全的发送 MIME 类型。

### 大小和上游要求

- 单个文件必须严格小于 50 MB。
- 同一条请求中的全部文件合计也必须严格小于 50 MB。
- Base64 会使 JSON 请求体约增加三分之一；反向代理或中转站建议将请求体上限设置为至少 72 MiB。
- PDF 中的扫描页、图片和图表需要上游模型支持视觉输入；非 PDF 文档中的嵌入图片和图表不保证进入视觉上下文，需要保留版式时建议先转换为 PDF。
- 上游必须完整支持 `/v1/responses` 的 `input_file.file_data`，否则应改用支持该能力的 Endpoint 或模型。

## 清理和兼容性

- 删除浏览器端附件本地文本/Office/PDF 解析逻辑及服务端 `server/extract` 实现。
- 移除 `mammoth`、`officeparser`、`pdf-parse`、`word-extractor` 运行依赖。
- 移除 `/api/extract-file` 接口、解析并发配置以及 Docker 中不再需要的解析工具包。
- 新上传文件不会生成本地提取文本；为兼容已有会话，历史记录中已经保存的旧提取文本仍可作为只读回退，不会被当作新文件解析。
- 增加了文件格式识别、MIME 推断、大小限制、原生 `input_file` 构造、历史附件恢复和请求体安全校验的回归测试。
