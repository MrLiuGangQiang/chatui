# 13 重新生成与编辑重发统一链路设计

## 1. 范围与目标

把「重新生成」收敛为「编辑重发」同一条提交链路。两者语义相同：都在原用户消息位置替换出一个新的 assistant 回复。唯一区别是输入文本来源：

- 重新生成：使用原用户消息原文，用户不修改。
- 编辑重发：用户在输入框修改后提交。

`client/app/regenerate-workflow.js` 不再复制路由、资源池、图片/批量/聊天执行和任务生命周期逻辑，只负责解析原用户轮次、准备编辑状态并委托 `client/app/submit-workflow.js` 的 `runSubmit`。

非目标：

- 不改变 `route_intent.v3`、`dispatch_contract.v1` 或任何协议契约。
- 不改变「强制生图」入口与待处理澄清重放的现有能力集合；它们继续作为薄适配器存在，后续如需统一再单独设计。
- 不在根 `app.js` 增加新业务逻辑。

## 2. 现状与根因

编辑重发链路（`submit-workflow.js#runSubmit`）已经包含：

- 输入预检、附件/引用恢复；
- 意图路由、澄清、资源池投影；
- chat / image / image_batch 三类执行与任务生命周期；
- 用户消息原位替换与 assistant 替换槽位；
- pending submit 持久化和恢复。

重新生成链路（`regenerate-workflow.js#regenerateAssistantMessage`）把以上大部分能力又实现了一遍，导致两条链路漂移。此前图片提示词重复拼接、资源池差异、批量投影差异都源于这种重复实现。统一后这些分支只保留一份事实源。

## 3. 目标流程

```text
点击 assistant 消息「重新生成」
  -> 解析前一条 user 消息轮次与原文
  -> 准备与编辑重发相同的编辑状态
       editingIndex / editingNode / editingQuoteContext
       恢复原 user 消息附件到 state.attachments
  -> submitWorkflow.onSubmit(事件, { promptOverride: 原文 })
  -> runSubmit
       input_preflight -> route_intent -> dispatch_contract
       -> 替换原 assistant -> chat/image/image_batch 执行
```

`promptOverride` 使提交链路不再读取输入框；编辑重发时为空则读取输入框。最终 `promptText` 都进入同一段处理代码。

## 4. 模块契约

- `createSubmitWorkflow().onSubmit(e, options)`：新增可选的 `options` 透传给 `runSubmit(e, options)`；DOM 表单调用仍为 `onSubmit(e)`，行为不变。
- `createRegenerateWorkflow` 保留对外接口 `regenerateAssistantMessage`、`forceImageFromUserMessage`；`regenerateAssistantMessage` 改为薄适配器。
- 编辑状态字段继续复用应用状态：`editingIndex`、`editingNode`、`editingQuoteContext`；由 `applyPendingEdit` 在提交开始时消费并清理。

## 5. 不变量与安全

- 所有执行仍经过 `dispatch_contract.v1`；重新生成不得绕过路由直接构造执行合同。
- 原附件恢复失败时，沿用编辑重发的失败语义，不发送缺资源的请求。
- 待处理澄清消息的「重新生成」按可恢复性分流：有可选项或自由文本槽位时重放 pending clarification；只有缺图片/文件槽位且没有可选项时，必须带原任务的 pending context 重新进入统一提交/路由，不能只重画同一问题。
- `quoteContext` 在消息、display item 和 DOM 边界统一通过 `messagePrimitives.quoteContextJson` 规范为 canonical JSON 字符串；重新生成只能复用该单一实现，不得使用 `String(...)` 或新增本地 serializer。结构化对象退化为 `[object Object]` 必须视为协议错误。
- 引用是否进入最终聊天 payload 只由最终 `dispatch_contract.context_policy.quoted` 决定；提交工作流不得保留 `quoteScopedChat` 等第二套本地权威。
- 重新生成/编辑重发提交前必须清理被替换用户轮次内的全部旧响应产物：旧 assistant、错误提示、重复输出、旧图片结果及其 display/DOM 记录。清理边界止于下一条用户消息，后续用户轮次不得被删除或改写。
- 重新生成/编辑重发的意图识别上下文只包含被替换用户轮次之前的消息；被替换的旧回复、其后所有消息、执行结果、候选和缓存提示都不进入路由模型，避免把未来上下文误当成当前依赖。
- 停止、取消、pending submit、job ownership 语义全部来自统一提交链路，重新生成路径不再单独实现。
- 会话处于 `stopping` 时点击「重新生成」不得静默返回；应在有界时间内等待停止终态，停止完成后继续原重生成流程。若仍有其他运行任务占用会话，必须给出明确的可操作提示。
- 替换轮次在提交时会留下空的 `replacing` assistant 槽位，但该槽位只是 canonical 状态位，不是完成证据，也不得由 `renderMessageFromCanonical` 创建空 DOM 消息；实时等待状态只能由有效的 pending display item 提供。刷新恢复必须先验证 durable job，只有非空正文或 durable 富媒体才能判定完成。没有 job、正文、思考、富媒体或输出阶段证据的空 pending item 必须丢弃，不能因会话仍忙而保留。

## 6. 验收标准

1. 对同一条用户消息分别执行「重新生成」和「编辑重发且不改文本」，两者的路由输入、currentTurn、资源池、dispatch contract 与执行请求相同，且意图上下文都不包含被替换轮次及其后的任何消息。
2. 编辑重发修改文本时，只有输入文本变化，其余链路步骤不变。
3. 图片重新生成最终使用 canonical dispatch prompt，不再出现「原文 + 解析指令」重复拼接（IMG-021 继续通过）。
4. 重新生成历史中间轮次时，清理该轮全部旧 assistant/error/重复输出和 media 结果，只保留一个新的替换槽位；后续用户轮次及其回答不被截断。
5. 待处理澄清重放、缺失资源澄清重试与强制生图行为不回归。
6. 重新生成/编辑重发正在输出时刷新，空的 replacement 槽位不得让恢复链路误判完成；服务端 Job 仍存在时必须继续查询并续接输出，Job 不存在时必须中断并清理，禁止自动重新提交。
7. `npm run check` 全量通过。
8. 用户在停止动画/停止收口期间点击重新生成，停止完成后同一意图必须自动继续；不能出现点击无响应。

## 7. 回归测试

- 重新生成以原文本调用统一 `submitWorkflow.onSubmit`，并携带正确编辑状态；
- 重新生成恢复原消息附件到编辑状态；
- 编辑文本路径与重新生成路径共用 `runSubmit`（同一实现、无 regenerate 独立路由分支）；
- 图片重新生成 prompt 不重复（保留 IMG-021 自动化回归）；
- 历史中间轮次重新生成清理该轮全部旧响应（含错误提示和旧图片结果）且不截断后续轮次；
- 轮次清理同时覆盖 canonical messages、display items 与 DOM 节点（`testReplacementCollapsesEveryTurnResponseAndKeepsLaterTurns`、`testDisplayCleanupRemovesEveryResponseArtifactForTheEditedTurn`、`testEditResendRemovesEveryTurnResponseNodeBeforeReplacing`）；
- 待处理澄清重放、缺失资源澄清重新提交与强制生图现有测试全部通过。
- 服务端 Job 不存在时不得调用 `registerChatStreamJob` 或 `startImageGenerationJob` 重新提交，必须清理恢复 owner 并呈现中断态。
- `test/unit/regenerate-workflow.test.js` 覆盖 stopping 期间等待后自动提交，以及运行中任务给出明确提示而不静默丢失点击。
