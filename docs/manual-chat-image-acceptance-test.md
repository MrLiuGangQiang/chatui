# ChatUI 聊天 / 生图核心业务手工测试用例

> 只测试核心业务链路：聊天、流式输出、停止、刷新恢复、思考、自动路由、生图、修图、图片引用、多图、附件和结果持久化。  
> 不包含服务器部署、统计、公告、可访问性等外围功能。  
> 测试地址：`http://127.0.0.1:8765`

## 一、测试前准备

### 1. 模型配置

至少准备以下能力：

- **聊天模型 C1**：支持流式聊天。
- **聊天模型 C2**：与 C1 不同，用于验证会话模型隔离。
- **思考模型 R1**：支持 GPT-5 `reasoning_effort`。
- **路由模型 T1**：能识别聊天、生图、修图和澄清。
- **生图模型 I1**：支持文本生图。
- **修图模型 I2**：支持 `/images/edits`，最好支持多图和 mask。
- **文件模型 F1**：支持 Responses API 的 `input_file`。

如果你的网关没有独立路由模型，路由模型留空，验证是否正确跟随聊天模型。

### 2. 图片夹具

准备这些图片，图片上加文字标记，方便确认有没有选错：

| 编号 | 文件 | 内容 |
|---|---|---|
| IMG-A | `target-red-mug.png` | 白桌面上的红色杯子，右下角文字 `TARGET-A`，1200×800 |
| IMG-B | `content-blue-bike.jpg` | 蓝色自行车，左上角文字 `CONTENT-B` |
| IMG-C | `style-watercolor.png` | 水彩风格山水图，文字 `STYLE-C` |
| IMG-M | `transparent-mask.png` | 与 IMG-A 同尺寸，杯子区域透明，其余区域不透明 |
| IMG-L | `large-photo.jpg` | 长边大于 2048 的大图 |
| IMG-W | `sample.webp` | WebP 图片 |
| IMG-BMP | `sample.bmp` | BMP 图片 |

### 3. 文件夹具

| 编号 | 文件 | 内容 |
|---|---|---|
| FILE-TXT | `notes.txt` | `CHATUI-TXT-ALPHA；负责人：林晨；截止日期：2026-08-31` |
| FILE-CODE | `sample.js` | `function answer(){ return 8642; }` |
| FILE-PDF | `searchable.pdf` | 第 2 页包含 `CHATUI-PDF-BETA` 和数字 `7319` |
| FILE-SCAN | `scanned.pdf` | 扫描图片中包含 `CHATUI-SCAN-GAMMA` 和数字 `4826` |
| FILE-DOCX | `sample.docx` | `CHATUI-DOCX-DELTA；预算 125000` |
| FILE-XLSX | `sample.xlsx` | Summary!B2 = `24680` |
| FILE-PPTX | `sample.pptx` | 第 2 页包含 `CHATUI-PPTX-EPSILON；状态：绿色` |

### 4. 通用判断

每条用例记录：

```text
状态：PASS / FAIL / SKIP
实际结果：
证据：截图、请求、回复文本、图片、Job ID
```

`SKIP` 只能用于当前确实没有对应模型能力的场景，例如没有修图模型时跳过修图用例，不能把失败记成 SKIP。

# A. 配置和模型

## CHAT-001 配置聊天、路由、生图模型

**步骤**

1. 打开“模型配置”。
2. 设置 Endpoint 和 API Key。
3. 聊天模型选择 C1。
4. 意图识别模型选择 T1。
5. 生图模型选择 I1。
6. 保存并刷新页面。

**预期**

- 三个模型选择保存成功。
- 刷新后选择仍然保留。
- 聊天请求使用 C1，路由请求使用 T1，生图请求使用 I1。

## CHAT-002 路由模型留空跟随聊天模型

**步骤**

1. 路由模型留空。
2. 聊天模型选择 C1。
3. 发送一次普通聊天和一次明确生图。

**预期**

- 两次路由判断都使用 C1。
- 不因为路由模型为空而报错。
- 生图执行仍使用 I1。

## CHAT-003 模型加载和模型类型

**步骤**

1. 点击“加载模型”。
2. 查看聊天模型、路由模型、生图模型下拉。

**预期**

- 模型列表加载完成。
- 聊天模型下拉不会把 embedding 模型当作聊天模型。
- 生图模型下拉能显示图片模型。
- 未知模型应有未知类型提示，不应导致下拉为空。

## CHAT-004 全局 System Prompt

**步骤**

1. 全局 System Prompt 填入：`每次回答最后单独一行输出 GLOBAL-OK。`
2. 保存。
3. 新建会话，发送：`只回复“测试”。`

**预期**

- 回答最后出现 `GLOBAL-OK`。
- 请求中包含全局 system prompt。

## CHAT-005 全局图片样式提示词

**步骤**

1. 全局图片样式提示词填写：`使用蓝紫色霓虹边缘光。`
2. 发送：`生成一张深蓝背景的白猫。`

**预期**

- 生图 prompt 包含用户要求和全局样式。
- 样式提示词不会出现在普通聊天请求中。

## CHAT-006 会话级模型和 Prompt 隔离

**步骤**

1. 会话 A 选择 C2，并设置会话 System Prompt：`最后输出 SESSION-A-OK。`
2. 会话 B 跟随全局 C1，不设置会话 Prompt。
3. A、B 各发送一条消息。

**预期**

- A 使用 C2，并执行 `SESSION-A-OK`。
- B 使用 C1，并不执行 A 的 Prompt。
- 切换和刷新后设置仍然正确。

# B. 普通聊天

## CHAT-007 普通流式聊天

**步骤**

发送：

```text
请分 10 行介绍 ChatUI，每行以 01 到 10 编号。
```

**预期**

- 回复逐步出现，不是等待结束后一次性显示。
- 只生成一条用户消息和一条助手消息。
- 最终内容完整，顺序正确。

## CHAT-008 多轮上下文

**步骤**

1. 发送：`记住暗号：海盐-7391。只回复已记住。`
2. 发送：`刚才的暗号是什么？只回复暗号。`

**预期**

- 第二轮回复 `海盐-7391`。
- 请求携带当前会话必要历史。
- 不携带其他会话内容。

## CHAT-009 椭圆追问

**步骤**

1. 发送：`比较 Python 和 JavaScript 的主要用途。`
2. 发送：`性能方面呢？`
3. 发送：`这个呢？请只解释你上一条中提到的第二项。`

**预期**

- 三轮上下文连续。
- 短句追问不会被误判为生图。
- 回复针对上一轮内容，而不是重新泛泛回答。

## CHAT-010 中文输入法提交

**步骤**

1. 使用中文输入法输入中文。
2. 在候选词组合期间按 Enter。
3. 组合完成后再次按 Enter。

**预期**

- 候选词 Enter 不提交消息。
- 组合完成后的主动 Enter 只提交一次。
- 不产生重复请求。

## CHAT-011 Enter 和 Shift+Enter

**步骤**

1. 输入 `第一行`。
2. 按 Shift+Enter。
3. 输入 `第二行`。
4. 按 Enter。

**预期**

- Shift+Enter 换行。
- Enter 发送。
- 用户消息保留两行。

## CHAT-012 大文本限制

**步骤**

1. 粘贴小于 120,000 字符的文本。
2. 再粘贴超过 120,000 字符的文本。

**预期**

- 限额内可以正常处理。
- 超限内容被拒绝并提示分段发送或改用文本文件。
- 页面不冻结，输入框布局不崩。

## CHAT-013 助手回答复制

**步骤**

1. 让助手输出标题、列表、代码和公式。
2. 点击“复制消息”。
3. 粘贴到纯文本编辑器。

**预期**

- 复制可见内容。
- 不包含复制按钮、下载按钮、HTML 控制标签。
- 代码内容完整。

## CHAT-014 用户消息复制和部分选择

**步骤**

1. 完整选择一条用户纯文本消息并复制。
2. 只选择其中几个字并复制。
3. 对带附件的用户消息执行复制。

**预期**

- 完整选择复制原始用户文本。
- 部分选择保持浏览器原生选择结果。
- 带附件消息不会把附件 UI 文案强行复制进去。

## CHAT-015 引用用户消息

**步骤**

1. 点击较早用户消息的“引用”。
2. 输入：`请只改写被引用内容，不要回答其他消息。`
3. 发送。

**预期**

- 输入区出现引用预览。
- 发送后用户消息保留引用关系。
- 模型只围绕引用内容回答。
- 引用不会改变用户消息正文对齐。

## CHAT-016 引用助手消息

**步骤**

1. 引用一条助手回答。
2. 输入：`总结这段回答，最多三点。`
3. 发送并刷新。

**预期**

- 引用角色显示为助手。
- 回复针对被引用回答。
- 刷新后引用关系仍保留。

## CHAT-017 编辑用户消息并重发

**步骤**

1. 发送：`2+2 等于多少？`
2. 完成后点击用户消息“编辑重发”。
3. 改为：`12+13 等于多少？`
4. 发送。

**预期**

- 原用户消息内容替换为新内容。
- 对应助手回复替换为 25。
- 不保留旧的 4 作为对应答案。
- 后续消息顺序不乱。

## CHAT-018 重新生成助手回复

**步骤**

1. 发送：`随机给出三个英文单词。`
2. 完成后点击助手消息“重新生成”。

**预期**

- 使用原用户消息和原附件上下文重新请求。
- 新回复替换旧回复，不新增到错误位置。
- 其他历史消息不变。

## CHAT-019 下载助手回答

**步骤**

1. 让助手输出中文、代码和公式。
2. 点击“下载回答”。
3. 用文本编辑器打开下载文件。

**预期**

- 下载成功。
- 中文无乱码。
- 文件不含操作按钮文字和图片 Base64。

## CHAT-020 回复完成提示音

**步骤**

1. 先点击页面解锁浏览器音频权限。
2. 发送短消息并等待完成。
3. 再停止一个长消息。

**预期**

- 正常完成时提示音播放一次。
- 停止和失败不播放完成音。
- 浏览器静音不会产生脚本错误。

# C. 流式输出、停止、刷新恢复

## CHAT-021 流式输出中停止

**步骤**

发送：

```text
请从 1 到 80 逐条输出，每条格式为“第NN条：这是用于刷新恢复测试的长输出”，不要省略，不要合并。
```

看到至少 5 条后点击停止。

**预期**

- 停止请求发出。
- 输出不再继续增加。
- 已经显示的内容保留。
- 发送按钮恢复可用。

## CHAT-022 输出中按 Enter 不应停止

**步骤**

1. 开始长输出。
2. 输出中把焦点放回输入框。
3. 按 Enter。

**预期**

- Enter 不会停止当前任务。
- 不会提交空消息。
- 只有点击停止按钮才中断输出。

## CHAT-023 首 token 前停止

**步骤**

1. 使用慢响应模型发送长消息。
2. 第一个正文出现前点击停止。

**预期**

- 不出现永久 loading。
- 显示用户停止或等价状态。
- 刷新后任务不会重新启动。

## CHAT-024 首个可见字符后立即刷新｜核心回归

**步骤**

1. 开始长输出。
2. 一看到助手正文第一个字符，立即按 F5。
3. 刷新后继续等待任务完成。

**预期**

- 刷新前已经显示的正文前缀不能丢失。
- 恢复后继续显示同一条助手消息。
- 不从空白开始。
- 不重复已经显示的前缀。
- 不产生第二条助手消息。

## CHAT-025 输出中多次刷新

**步骤**

1. 开始长输出。
2. 输出中刷新 3 次，每次间隔 1–2 秒。
3. 等待最终完成。

**预期**

- 每次刷新后的已显示内容都不会比刷新前更少。
- 最终内容完整、顺序正确、无重复。
- 会话中只有一条对应助手消息。

## CHAT-026 输出完成后刷新

**步骤**

1. 等待长回答完成。
2. 立即刷新。
3. 再切换会话后回来。

**预期**

- 完整回答保持不变。
- 不重新显示“正在输出”。
- 不重新创建 Job。

## CHAT-027 输出中切换会话

**步骤**

1. 会话 A 开始长输出。
2. 切换到会话 B。
3. B 发送普通消息。
4. 等待 A 和 B 都完成。

**预期**

- A 和 B 的输出互不覆盖。
- B 不显示 A 的流式内容。
- 回到 A 时显示完整 A 结果。
- 两个会话各自只有一条助手消息。

## CHAT-028 SSE 断开后恢复

**前置**：有可断开 SSE 的测试网关；没有则 SKIP。

**步骤**

1. 开始长输出。
2. 中途断开 SSE 连接数秒。
3. 恢复网络。

**预期**

- 前端重连或轮询任务。
- 已显示内容不清空。
- 最终结果与服务端任务一致。
- 不重复发起一次完整生成。

## CHAT-029 服务重启后的任务恢复

**前置**：允许手动重启当前 ChatUI 服务；没有则 SKIP。

**步骤**

1. 开始长输出。
2. 输出中重启服务。
3. 刷新页面。

**预期**

- 若服务端内存 Job 丢失，显示明确“任务不存在/服务已重启”。
- 用户消息和已经持久化的输出保留。
- 本地 pending/busy 状态被清理。
- 新消息仍然可以发送。

## CHAT-030 停止后刷新不得复活

**步骤**

1. 开始长输出。
2. 看到部分内容后点击停止。
3. 立即刷新并等待 10 秒。

**预期**

- 停止后的内容不再增加。
- Job 不会复活。
- 不重复播放完成音。

# D. 思考模式

## CHAT-031 思考模式默认关闭

**步骤**

1. 新建会话。
2. 观察思考开关和强度菜单。
3. 关闭思考后发送一次普通问题。

**预期**

- 默认关闭。
- 关闭时强度菜单不可用。
- 关闭状态的请求不含 `reasoning_effort`。

## CHAT-032 思考强度透传

**步骤**

对 `low`、`medium`、`high`、`xhigh`、`max` 分别发送：

```text
计算 37×48，并简要说明过程。
```

**预期**

- 每次请求的 `reasoning_effort` 与选择完全一致。
- 不把 `max` 自动改成 high。
- 不发送旧的 `minimal` 参数。

## CHAT-033 思考内容显示与折叠

**步骤**

1. 开启思考。
2. 发送需要推理的问题。
3. 完成后展开和收起思考区。

**预期**

- 思考内容位于最终答案上方的独立区域。
- 展开/收起不影响最终答案。
- 刷新后思考内容和最终答案都保留。

## CHAT-034 思考模式流式锁定

**步骤**

1. 开启 high。
2. 发送长推理任务。
3. 输出期间尝试切换强度和关闭开关。

**预期**

- 设置被锁定或给出明确提示。
- 本次请求参数不被中途改变。
- 完成后恢复可操作。

## CHAT-035 不支持思考的模型

**步骤**

1. 选择不支持 reasoning 的模型。
2. 开启 high。
3. 发送问题。

**预期**

- 显示上游明确错误。
- 不静默降级为普通聊天。
- 错误后发送按钮恢复，下一次普通聊天仍可用。

# E. 自动路由

## CHAT-036 普通聊天路由

**步骤**

发送：`法国首都是哪里？`

**预期**

- 走 chat/plain_chat。
- 不调用图片生成或编辑接口。
- 最终显示文本回答。

## CHAT-037 文本生图路由

**步骤**

发送：

```text
生成一张方形图片：深蓝背景，中央是一只戴黄色围巾的白猫。
```

**预期**

- 走 image/text_to_image。
- 调用图片生成接口。
- 不先生成聊天解释来代替图片。

## CHAT-038 图片编辑路由

**步骤**

1. 上传 IMG-A。
2. 发送：`只把红色杯子改成绿色，保留桌面和 TARGET-A。`

**预期**

- 走 edit_image。
- IMG-A 作为目标图。
- 调用图片编辑接口。
- 不调用纯文本聊天作为替代。

## CHAT-039 用户消息强制生图

**步骤**

1. 发送：`一个未来城市的视觉概念`。
2. 对该用户消息点击“强制生图”。

**预期**

- 使用原用户消息直接进入生图。
- 不再误走普通聊天。
- 图片结果关联到正确消息和会话。

## CHAT-040 非图片附件走文件聊天

**步骤**

1. 上传 FILE-TXT。
2. 发送：`告诉我附件中的负责人和截止日期。`

**预期**

- 走文件问答聊天。
- 不进入图片编辑。
- 回答包含 `林晨` 和 `2026-08-31`。

## CHAT-041 模糊生图需求澄清

**步骤**

发送：`帮我做一张产品海报。`

**预期**

- 信息不足时提出澄清问题。
- 不凭空选择尺寸、主体和风格后直接执行。
- pending 任务保留原始需求。

## CHAT-042 多轮澄清

**步骤**

1. 对 CHAT-041 回复：`橙色科技风`。
2. 如果继续追问，再回复：`竖版，标题写“夏日新品”。`

**预期**

- 所有补充都进入同一个任务。
- 最终生图 prompt 包含原始需求和所有补充。
- 只执行一次最终生图。

## CHAT-043 澄清期间发起新任务

**步骤**

1. 让一个生图请求进入澄清。
2. 直接发送：`忽略刚才的海报，解释 HTTP 404。`

**预期**

- 新消息按普通聊天处理。
- 不继承旧任务的图片操作或图片资源。
- 旧 pending 状态按产品规则清理或保留，但不能污染新任务。

## CHAT-044 当前图、上一张图、引用图

**步骤**

1. 上传 IMG-A 并编辑得到 G1。
2. 引用 G1 发送：`把它的背景换成雪山。`
3. 不引用任何图片，发送：`把上一张图的杯子变成蓝色。`

**预期**

## 最终判定

- 普通聊天、流式输出、停止、刷新恢复、会话隔离全部通过，才算“聊天基本可用”。
