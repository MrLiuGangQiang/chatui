# 29 皮肤独立分层与按需加载设计

> 状态：阶段 1-3 已实现并提交（2026-09-16/17），阶段 4 本次提交。所有基础样式表已全部令牌化（约 1828 个控制点），两套皮肤均添加了域令牌覆盖。本文在 27 号文档基础上重构皮肤的样式分层与加载机制，落实两条硬要求：一是每套皮肤可独立细粒度控制且互不影响；二是加载机制按需、顺序稳定、首屏不闪。与 27 冲突之处以本文为准；皮肤 id 目录、持久化键与切换器交互契约沿用 27。

## 1. 范围与目标

- 需求一（独立控制、互不影响）：皮肤可控制到任意视觉细节（每套皮肤各自的侧栏透明度、玻璃模糊强度、选中会话强调、纹理装饰等），改一套皮肤永远不需要另一套皮肤写对抗样式，也不需要回写共享文件。
- 需求二（加载机制合理）：页面只加载公共基础样式与当前激活皮肤；非激活皮肤的 CSS 与图片不下载；样式到达顺序不影响优先级；开发期皮肤文件即改即见；首屏不闪烁、无布局位移。
- 手段：样式重组为基座（base）、视觉域（surfaces）、皮肤（skins）、评审后覆盖（overrides）四层，用浏览器原生 CSS @layer 在 bundle 装配时定序；非默认皮肤改为运行时按需注入单个样式链接。
- 非目标：不改业务逻辑；不改皮肤数据模型、持久化与切换交互；不引入构建步骤；迁移完成后三套皮肤外观与现状一致（见第 7 节视觉验证）。

> **方案修订记录**：初稿以 CSS `@layer` 作为"皮肤稳定压过基础样式"的地基。实现前验证否决了该路径——本仓库样式表含约 9400 个 `!important`（styles.css 2867、flat-theme.css 2999、skins/ink 1960 等），而 `@layer` 对 `!important` 声明的层叠方向**相反**（越早的层越赢），直接包裹会瞬间翻转基础层与皮肤层的胜负，三套皮肤全部花屏。改用「按需注入 + 顺序垫底」（§3）后，同样两条要求可以立刻兑现且零视觉风险；`!important` 治理降级为阶段 2 的渐进清理目标（棘轮门禁），不再是分层前提。

## 2. 样式分层与装配契约

```text
styles/
  base/            基座：reset、布局几何、动效骨架、焦点可访问性；皮肤禁改
  surfaces/        视觉域：每个域一个文件，一切可被皮肤感知的视觉决策都在这里
  skins/<id>/      皮肤自治目录：令牌覆盖 + 细粒度直接规则 + 同目录资产
  (overrides)      评审后的皮肤后覆盖样式（现：message-actions-text.css）
```

层叠优先序即装配顺序，从高到低固定为：

```text
overrides（post-skin 静态 head 链接） > 激活皮肤（boot 注入链接） > skins/default（bundle 内） > surfaces > 主题与基座
```

- 非默认皮肤不再是 manifest 条目，由 boot 脚本按激活状态注入到 bundle 之后、overrides 链接之前，因此"皮肤永远压过基础、但压不过评审后功能覆盖"这一关系与迁移前完全一致。
- `index.html` 的 manifest 仍是有构建约束下的唯一装配事实源；新增皮肤不登记 manifest。
- `server/http/static.js` 与 `server/services/static-bundle.service.js` 无需改动：`/styles/` 前缀本就放行皮肤直链，CSS 维持 `no-store`。

## 3. 「按需注入 + 顺序垫底」如何兑现互不影响

需求拆成三条互不干扰的性质，各自由一个机制保证：

| 性质 | 保证机制 |
| --- | --- |
| 皮肤 A 不可能影响皮肤 B | 同一时刻文档里只存在 default + 激活皮肤两套样式，未激活皮肤的规则**根本不在场** |
| 皮肤能压过基础样式 | 皮肤链接位于 bundle 之后（DOM 顺序垫底），同权重下后者胜，无需堆权重 |
| 皮肤不会破坏基础骨架 | 皮肤目录禁改布局/几何/显隐/焦点（§8 门禁），基础层修 bug 不波及皮肤 |

- 现状的约 9400 个 `!important` 因此不再是分层前提：本机制不依赖权重对抗，皮肤可以在自己的文件里用普通规则达成细粒度控制。
- `!important` 仍是需要清理的债务（它让"皮肤只写一行就生效"在部分表面失效），但降级为阶段 2 的渐进目标：base/surfaces 侧新增禁止、存量按棘轮基线只降不升；`styles/skins/` 侧禁止新增。
- 已知残留：阶段 1 的示范域仍带 `!important`（与基础层同权重），因为若去掉，默认皮肤的侧栏材质会被 `styles.css` / `flat-theme.css` 的 important 规则压制。该 important 属存量迁移而非新增升级，域文件注释已标注其解除条件。

## 4. surfaces 视觉域与控制点

- 域划分（每域一个文件；首波建立边界与注释，后续波次迁入条目）：session-sidebar、topbar、messages、markdown、code-block、composer、dialogs、welcome、image-grid、usage-stats、announcement、skin-switcher。
- 域文件头部是机器可校验的注释模板，声明本域「控制点表（名称 + 语义）」与「皮肤禁改项」：

```css
/* 域：会话侧栏
 * 控制点（皮肤覆盖即可整体调节）：
 *   --sidebar-fill       侧栏底色，含透明度（例 rgba(255,255,255,.20)）
 *   --sidebar-veil       侧栏渐变罩纱
 *   --sidebar-border     侧栏分隔描边
 *   --sidebar-blur       毛玻璃模糊半径
 *   --sidebar-saturate   毛玻璃饱和度
 * 皮肤禁改：宽度、折叠断点、滚动行为、焦点顺序
 */
.session-sidebar { backdrop-filter: blur(var(--sidebar-blur)); }
```

- 控制点是**推荐旋钮，不是许可白名单**：皮肤在 §5 第②段写直接规则完全合法；控制点只保证高频调节项拥有跨皮肤稳定的名字（例：每套皮肤的侧栏透明度、模糊半径）。
- surfaces 引用的每个控制点必须在默认皮肤中定义权威默认值——默认皮肤因此升格为"全部控制点的默认层"，新皮肤只覆盖自己关心的子集。
- 过渡期约束：当某域的基础材质尚未被全部皮肤用控制点表达时，域规则必须限定 `html[data-skin="default"]`，否则会以后写默认值命中其他皮肤的边框/背景简写。各皮肤改用控制点后摘除该前缀（阶段 3），摘除进度由 §8 的 `testTransitionalDefaultScopeInsideSurfacesShrinksOnly` 基线跟踪，禁止新增。
- `styles/skin-system.css` 中逐皮肤点名的 `.skin-swatch-<id>` 色板规则待移入各皮肤①段（`--skin-swatch` 令牌驱动），使切换器外壳不再知道任何具体皮肤；本项在阶段 3 与皮肤重编一并完成。

## 5. 皮肤目录自治契约

`styles/skins/<id>/skin.css` 三段式（段注释是门禁识别锚点）：

1. **① 令牌段**：覆盖 `--skin-*`、域控制点与（阶段 3 起）`--skin-swatch`；
2. **② 直接规则段**：细粒度个性定制，一律限定 `html[data-skin="<id>"]` 作用域；
3. **③ 资产**：同目录相对引用（如 `url("./scenery.jpg")`），随皮肤共存亡。

- **新增一套皮肤 = 建 `styles/skins/<id>/` + 在 `client/core/skin.js` 注册一行 + 在 `index.html` 首屏白名单加入 id + 在 `styles/skin-system.css` 增加一个 `.skin-swatch-<id>` 色板**；manifest、切换器逻辑与业务共享文件零改动（§10 验收 4）。
- 皮肤资产必须以相对路径引用同目录文件，不得 `url("../…")` 逃逸、不得 `@import`——因为它现在是被独立加载的一份样式，脱离 bundle 后没有任何路径重写兜底。
- `styles/skins/` 之外禁止出现指向某套具体皮肤的 `data-skin="<id>"` 选择器（boot 脚本与过渡期域前缀除外，见 §4）。

## 6. 加载机制（阶段 1 已实现）

- manifest 的 CSS 清单只保留 `styles/skins/default/skin.css`：默认皮肤零额外请求、首屏同步生效；snow、ink 两条目已删除。
- `client/core/skin.js` 新增纯函数 `skinStylesheetHref(id)`：default 返回空串（在 bundle 内），其余返回 `/styles/skins/<id>/skin.css`；未知 id 归一 default 并返回空串（失败关闭，绝不拼出无效请求）。
- boot 内联脚本在设置 `data-skin` 后按 `skinStylesheetHref` 的结果注入唯一一条 `<link data-chatui-skin="<id>">`，并插入到 `link[data-chatui-post-skin]` **之前**：overrides 链接由解析器在脚本执行之后才进入 head，因此皮肤注入时锚点尚不存在，脚本显式处理两种情形。
- 运行时切换：`client/features/skin-system/skin-switcher.js` 的 `syncSkinStylesheet(skinId)` 维护**同一条**皮肤链接——切换改 href、切回 default 移除链接、缺失锚点则追加到 head 尾部；`refresh()` 也会采纳 boot 留下的链接，使 DOM、存储与可见样式表三者始终一致。
- 缓存：皮肤直链沿用既有 `/styles/` 前缀放行与 `no-store`，服务端逻辑不改，开发即改即见；bundle 内 default 皮肤仍走 `url()` 公共路径重写，直链皮肤的相对 `url()` 由浏览器按请求路径解析，天然指向自己的目录。
- 可选增强（不列入验收）：由注册表驱动对非激活皮肤 `<link rel="preload">` 空闲预热，实现切换零等待。

## 8.1 样式文件编码纪律（阶段 1 事故记录）

阶段 1 实施中发生过一次真实回归：`styles/skins/default/skin.css` 经 PowerShell 默认代码页（GBK/936）读改写后，注释终止符 `）*/` 被破坏成 `锛?/`，形成**未闭合注释**，浏览器随即吞掉其后的全部声明——包括新的 `--sidebar-*` 控制点与既有的 `--bg/--ds-*/--chatui-*` 别名层。当时的字符串包含式断言仍然全绿，属于假绿。

约束（已由门禁固定，不是口头约定）：

- 含非 ASCII 内容的样式/脚本文件，编辑必须显式走 UTF-8 读写路径，不得依赖 shell 默认编码；
- `testSkinStylesheetsAreByteExactUtf8` 要求皮肤相关样式表字节级 UTF-8 往返一致、无 U+FFFD、`/*` 与 `*/` 数量平衡；
- `testSidebarControlPointsAreLiveCss` 先剥注释再断言，保证控制点与别名层是**浏览器可见的活 CSS**，而不是文件里的字符串；
- `testSidebarControlPointsPinThePreMigrationValues` 钉住迁移前的精确值（宽松上下界不足以发现 `.20 → .90` 这类可见漂移）。

三条门禁均已反证：重放未闭合注释与值漂移时分别 fail，还原后恢复通过。
## 9. 边界与否决方案

- **否决 CSS `@layer`**（本设计初稿方案）：`@layer` 对 `!important` 声明反向排序，本仓库约 9400 个 important 会让包裹瞬间翻转基础层与皮肤层胜负；要安全使用需先地毯式清空基础层 6500+ 个 important，风险与本收益完全不成比例。否决理由与数据见 §3。
- 否决「每套皮肤全量复制基础样式」：布局 bug 需改 N 份，皮肤一多必然漂移；三层结构 + §5②段直接规则已提供同等细粒度。
- 否决「运行时 JS 注入样式对象」：破坏「皮肤 = 纯 CSS 文件」模型，与 module-registry、bundle 边界打架。
- 不使用 `@import` 加载皮肤：多一次串行往返，且无法由 boot 按激活状态条件触发。
- 不做：端口、静态缓存策略、根静态入口保护名单均不变；`styles/skins/_shared/` 共享材质库留作演进方向，本设计不预留。
