# 18 图片清晰度提升设计

> 状态：设计基线，已进入实现。
> 日期：2026-09-12
> 关联文档：`16-图片编辑工具设计.md`、`04-API与服务契约设计.md`

## 1. 范围与目标

在图片编辑工作台增加“画质提升”工具。用户选中该工具后点击“应用”，系统使用当前图片作为唯一 `target`，通过现有 `edit_image` 通道生成清晰度增强后的图片。

目标：

- 增强细节、纹理、边缘和局部对比度，减少模糊、噪点与压缩伪影；
- 保持原图宽高比、构图、主体身份、姿态、颜色、光照、风格和文字内容；
- 不要求用户涂抹或填写参数，一键确定执行；
- 复用现有图片任务生命周期、取消、失败提示和结果持久化。

非目标：

- 不提供真正的像素级超分辨率或无损恢复；
- 不新增 HTTP 接口、服务端存储、数据库字段或依赖；
- 不改变普通聊天、生图、评论、移除背景和局部擦除的语义；
- 不允许模型添加、删除、替换或重绘原图内容。

## 2. 流程与状态

```text
图片编辑工作台
  -> 选择“画质提升”
  -> 画布只读，工具状态显示说明
  -> 点击“应用”
  -> edit_image(target=原图, prompt=清晰度增强提示词, mask=无)
  -> 现有图片任务通道执行、取消、恢复和持久化
  -> 生成新的 assistant 图片结果
```

编辑器状态追加：

```text
tool = 'enhance'
```

`enhance` 属于无画布操作模式：

- 不创建 mask，不读取涂抹数据，不要求评论；
- 画布 overlay 不接收指针事件；
- “撤销 / 重置 / 清空”保持禁用；
- 点击其他工具可正常切换；
- 关闭或取消不提交。

## 3. 数据与接口契约

- `operation=edit_image`、`api=image_edit`；
- bindings 仅包含一张 `role=target` 的图片；
- 不传 mask；
- 不增加 `size`、`background`、`output_format` 等参数覆盖；
- 用户消息默认显示“提升图片清晰度”；
- 模型提示词固定为：

```text
提升这张图片的清晰度。增强细节、纹理、边缘和局部对比度，减少模糊、噪点与压缩伪影；保持原始构图、主体、姿态、颜色、光照、风格和文字内容不变，不要添加或删除任何元素。
```

- 结果继续使用现有图片生成结果渲染与持久化路径。

## 4. 安全与错误边界

- 该操作由编辑器按钮发起，属于确定性操作，不经过意图模型；
- 图片内容仍通过受控 `edit_image` 代理，不新增外部请求目的地址；
- 日志不得记录图片 base64、签名 URL 或凭据；
- 上游不支持编辑、模型失败或网络失败时沿用现有中文可操作错误提示，不伪装成功；
- 没有 mask 是合法状态，不得被旧有“编辑必须带 mask”逻辑误判。

## 5. 验收标准

1. 工具栏展示“画质提升”，且可与其他工具切换；
2. 选中后画布只读，撤销、重置、清空不可用；
3. 点击“应用”只提交一张 target，不提交 mask；
4. dispatch contract 为 `operation=edit_image`、`api=image_edit`；
5. 提示词包含清晰度增强和内容保持约束；
6. 用户消息显示“提升图片清晰度”；
7. 取消不产生请求；
8. 请求失败时释放任务状态并显示既有可操作错误。

## 6. 回归测试

- `test/unit/image-editor-mask.test.js`：冻结清晰度提升提示词的内容和约束；
- `test/unit/image-editor-single-surface.test.js`：验证工具按钮、只读状态、取消和提交结果；
- `test/unit/image-editor-workflow.test.js`：验证只提交 target、不提交 mask、用户消息和 dispatch contract；
- `npm run check`：全量项目、架构、语法和测试门禁继续通过。

## 7. 演进边界

后续如增加“低清修复 / 老照片修复 / 放大倍率”等能力，应作为独立工具或参数化编辑设计，不能静默改变“画质提升”的语义。真正超分辨率需要独立模型与明确的能力探测，不在本设计范围。
