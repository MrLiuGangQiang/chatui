# 21 图片尺寸调整设计

> 状态：设计基线，已进入实现。
> 日期：2026-09-13
> 关联文档：`16-图片编辑工具设计.md`、`19-图片编辑混合操作设计.md`、`20-图片编辑记录编辑删除设计.md`、`04-API与服务契约设计.md`

## 1. 范围与目标

在现有图片编辑工作台中恢复“调整尺寸”能力，对齐 ChatGPT 图片编辑器的宽高比选择界面：

- 左侧工具栏提供“调整尺寸”入口，点击后在图片附近展开“用不同宽高比生成此图片”菜单；
- 一次只保留一个尺寸操作历史，支持方形、竖版、故事版、横版和宽屏五档；
- 尺寸记录与评论、擦除、画质提升共用右侧“操作历史”，点击“提交修改”时合并为一次 `edit_image` 请求；
- 请求继续使用现有 `size` 参数透传链路，不新增服务端接口、任务类型或持久化字段；
- 提示词要求保持主体、内容、颜色和风格，并按目标画幅自然扩展、补全或重新构图，避免拉伸变形和无意义裁切。

五档预设如下，所有宽高均为 16 的倍数，并满足 `shared/image-size-policy.js` 的宽高比、边缘和像素约束：

| 名称 | 比例 | 输出尺寸 |
| --- | --- | --- |
| 方形 | 1:1 | 1024x1024 |
| 竖版 | 3:4 | 1152x1536 |
| 故事版 | 9:16 | 864x1536 |
| 横版 | 4:3 | 1536x1152 |
| 宽屏 | 16:9 | 1536x864 |

官方 Images edit API 依据：支持 `size`；GPT Image 2 / 2.5 系列支持任意 `WIDTHxHEIGHT`，宽高必须为 16 的倍数，比例在 1:3 到 3:1 之间，最大分辨率 3840x2160。产品仍以当前部署模型的实际上游能力为准，上游不支持或拒绝自定义尺寸时必须诚实失败，不回退到其他尺寸或静默降级。

非目标：

- 不提供任意数值尺寸输入、裁剪框或缩放画布交互；
- 不做多轮模型编排，不把尺寸调整拆成多次 `edit_image`；
- 不允许调整尺寸与“移除背景”同时提交，继续遵守移除背景只能单独执行的能力约束；
- 不改变设置页的生成尺寸策略；尺寸记录只作用于当前编辑请求。

## 2. 流程与状态

```text
打开图片编辑器
  -> 点击“调整尺寸”
      -> 展开“用不同宽高比生成此图片”菜单
          -> 选择方形 / 竖版 / 故事版 / 横版 / 宽屏
              -> 用新尺寸替换已有尺寸记录（最多一条）
              -> 右侧操作历史显示“调整尺寸”卡片
  -> 可继续标记评论、擦除或画质提升
  -> 点击“提交修改”
      -> 只有尺寸记录：不生成 mask，提交 target + prompt + size
      -> 与评论 / 擦除组合：生成一张与源图同尺寸的 mask，提交 target + mask + prompt + size
      -> 与画质提升组合：合并为同一提示词和一次请求
      -> 与移除背景组合：本地失败关闭，不发送请求
```

编辑器新增内存状态：

```text
{
  resizeMenuOpen: false,
  history: [
    ...,
    {
      id,
      type: 'operation',
      operation: 'resize',
      presetId,
      label,
      ratio,
      width,
      height,
      size
    }
  ]
}
```

- 尺寸记录始终最多一条；再次选择其他比例时替换原记录，不追加第二条；
- 删除尺寸记录后工具栏入口恢复未选中状态；
- 重置和撤销继续操作同一份 `history`，尺寸记录不单独维护不可见状态。

## 3. 数据与执行契约

- 沿用 `operation=edit_image`、`api=image_edit`；不改变 dispatch contract 协议；
- `arguments.size` 传入选中的 `WIDTHxHEIGHT`，参数由 `shared/image-size-policy.js` 和 capability registry 统一校验；
- 只有尺寸记录时不发送 mask；与评论或擦除组合时，mask 仍与干净源图同宽高，不按目标比例重采样；
- 提示词由确定性的 `buildResizePrompt` 生成，再由现有组合提示词函数按“局部修改 -> 画质提升 -> 调整画幅”的顺序合并；
- 用户消息使用稳定、可读的中文标签，例如“调整图片尺寸为宽屏 16:9（1536 × 864）”；
- 尺寸记录与移除背景混用时返回既有本地提示，不发起网络请求；
- 目标图片始终是干净原图，尺寸记录不得扩展 mask、改写资源绑定或引入服务端持久化数据。

## 4. UI 与交互契约

- 工具栏按钮文案为“调整尺寸”，带画幅/裁切图标，并排在左侧工具栏工具列表最后；它保持正常文档流，不吸附到面板底部；
- 菜单标题固定为“用不同宽高比生成此图片”，选项固定为方形 1:1、竖版 3:4、故事版 9:16、横版 4:3、宽屏 16:9；
- 菜单在当前按钮下方展开，宽度受视口约束；点击菜单外或按 Escape 关闭且不添加记录；
- 选择比例后菜单关闭，对应选项显示选中状态，按钮进入选中状态，右侧出现可删除的“调整尺寸”记录；
- 选择尺寸不会自动提交，仍由“提交修改”统一提交，避免丢弃其他操作历史；
- 调整尺寸入口不抢占评论/擦除的画布指针状态；打开菜单时结束当前画布工具交互。

## 5. 安全与错误边界

- 菜单只渲染固定预设，不把用户输入拼接到 HTML；尺寸值只来自内置白名单；
- 尺寸参数在本地路由编译和能力校验阶段再次验证，非法尺寸不得离开客户端；
- 尺寸单独存在时不得携带 mask；尺寸与移除背景混用时必须在本地失败关闭；
- 上游拒绝尺寸或返回失败时沿用现有图片任务错误提示和日志脱敏规则，不回退到 `auto` 或设置页尺寸；
- 不新增凭据、SQL、服务端文件或浏览器全局变量。

## 6. 验收标准

1. 图片编辑器工具栏显示“调整尺寸”，菜单标题和五个宽高比选项与本文一致；
2. 选择任意比例后只增加一条尺寸记录，再次选择其他比例替换原记录；
3. 尺寸记录可删除，删除后按钮和菜单选项选中状态同步清除；
4. 只调整尺寸时提交恰好一张目标图、无 mask，并携带对应 `size`；
5. 调整尺寸与评论或擦除组合时仍只提交一次 `edit_image`，携带一张目标图、一张合并 mask 和对应 `size`；
6. 调整尺寸与移除背景组合时保持编辑器打开、显示可操作提示且网络请求为零；
7. 提示词包含目标比例和尺寸，并要求保持内容、自然补全、避免拉伸和裁切；
8. 原有评论、擦除、移除背景、画质提升、撤销、重置、删除记录和任务生命周期行为不回归。

## 7. 回归测试

- `test/unit/image-editor-mask.test.js`：尺寸提示词包含目标比例、输出尺寸和自然重构图约束；组合提示词保留局部修改和画质提升并加入尺寸调整；
- `test/unit/image-editor-single-surface.test.js`：菜单标题与五个选项、选择后生成一条尺寸记录、替换与删除同步、尺寸与移除背景混用失败关闭；
- `test/unit/image-editor-workflow.test.js`：尺寸编辑只提交目标图且无 mask，`dispatchContract.arguments.size` 与用户消息标签正确；
- `npm run check`：项目检查、架构检查、语法检查和全量测试继续通过。

## 8. 演进边界

若后续需要任意尺寸输入、围绕主体智能裁切或按比例直接生成而不进入操作历史，应另行设计尺寸策略、资源投影和结果展示，不得在当前实现中绕过统一预览、mask、提示词与提交链路。
