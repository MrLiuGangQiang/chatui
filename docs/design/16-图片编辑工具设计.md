# 16 图片编辑工具设计

> 状态：一期（擦除 / 移除背景 / 调整尺寸）已实现并通过 `npm run check`；二期（标注 / 评论）与三期（多轮编辑）在本文档后续补充。
> 日期：2026-09-11

## 1. 范围与目标

对齐 ChatGPT 图片编辑工具栏的产品形态，在聊天中的图片消息上提供就地编辑能力，复用现有 `edit_image` + mask + 参数透传链路，不新开服务端接口。

一期（本文档范围为验收基线）：

- 擦除：在图片上涂抹选区，生成 alpha mask，按 `image + mask + prompt` 调用图片编辑；
- 移除背景：一键编辑，`background=transparent` + `output_format=png/webp`；
- 调整尺寸：预置尺寸与自定义尺寸（`size` 参数，含 2.5 系列任意分辨率约束）。

二期：标注（画笔/箭头/矩形/文字合成标注图作为编辑输入）、评论（编号评论点转编辑指令）。

三期：对齐 ChatGPT 多轮编辑体验（Responses API `image_generation` 工具、`action=edit`、`input_image_mask`、`previous_response_id`）。

非目标：

- 不做图层、蒙版布尔、专业修图能力；
- 不引入服务端图片存储、新 HTTP 接口或数据库；
- 不改变普通聊天/生图的意图路由语义：编辑器发起的编辑是确定性操作，不经过意图模型。

## 2. 官方能力依据

OpenAI 官方文档（developers.openai.com）：

- Image generation 指南（`/api/docs/guides/image-generation`）：edits 端点支持编辑已有图片、多图参考、`image + mask` 局部编辑；
- Images edit API（`/api/reference/resources/images/methods/edit`）：`mask`、`input_fidelity`、`background`、`size`、`quality`、`output_format`、`output_compression` 参数；
- mask 要求：与源图同格式同尺寸、小于 50MB、必须含 alpha 通道；多图输入时 mask 只作用于第一张；
- GPT Image 的 mask 是 prompt-based 指导，模型可能不严格遵循精确保形状，因此提示词必须描述编辑意图；
- 透明背景仅支持 `png`/`webp` 输出；
- 自定义尺寸：宽高为 16 的倍数、比例 1:3 至 3:1、单边不超过 3840、总像素 655,360 至 8,294,400。

## 3. 流程与状态

```text
图片消息（assistant / user 图片）
  -> 点击"编辑"按钮
      -> 编辑器打开（模态 canvas，不进入消息历史）
          |- 擦除：涂抹选区 -> 生成与源图同尺寸的 alpha mask
          |- 移除背景：无需画布操作
          |- 调整尺寸：选择预置或输入自定义尺寸
      -> 点击"应用"
          -> 构造确定性 edit_image 请求（原图 + mask / 参数 + prompt）
          -> 现有图片任务通道执行（loading / 取消 / 失败提示复用）
      -> 结果写入新的 assistant 图片消息，可继续引用编辑
```

编辑器状态（内存，关闭即释放）：

```text
{ imageBlob, width, height, tool, brushSize, strokes[], maskBlob?, size? }
```

## 4. 数据与契约

mask 生成规则：

- 与源图同宽高；PNG；带 alpha 通道；
- 涂抹覆盖区域为透明像素（待编辑区域），其余为不透明白色（保持区域），符合 OpenAI mask 语义。

编辑请求：

- `operation=edit_image`，`api=image_edit`；
- bindings：`target` 图片（source 取原图来源）+ `mask` 图片（role=mask，最多 1 张，服务端已有约束）；
- arguments：`prompt`，可选 `size` / `background` / `output_format` / `quality` / `input_fidelity`；
- 固定提示词（英文，与现有图片管线一致，便于上游理解）：
  - 擦除：`Remove the selected area and fill it naturally with the surrounding background.`
  - 移除背景：`Remove the background and keep the subject cleanly cut out.`

尺寸校验（`shared/image-size-policy.js`，浏览器与能力注册表共用）：

- 预置：`auto`、`1024x1024`、`1536x1024`、`1024x1536`；
- 自定义：宽高为 16 的倍数、比例 1:3 至 3:1、单边 ≤3840、总像素 655,360 至 8,294,400；
- 校验失败返回可操作中文提示，不静默截断。

参数通道：

- `edit_image` 使用独立的参数 schema（`IMAGE_EDIT_ARGUMENTS`）：`size` 为 `image_size` 类型且允许显式 override，供编辑器的"调整尺寸"传递用户选择；
- 生成路径（`text_to_image` 等）保持原不变量：尺寸只由设置页决定，文本解析、模型输出与澄清都不会改变它；
- 移除背景通过 override 传 `background=transparent` 与 `output_format=png`。

## 5. 前端行为

- 图片消息内直接显示与 ChatGPT 一致的五项工具条：标注、评论、移除背景、擦除、调整尺寸；仅当图片可恢复为 Blob 时可用；
- 工具条匹配所有生成图（渲染时临时 blob/data 源属性会被剥离，不能依赖 data-persisted-src）；图片来源在使用时按 persistedSrc → originalSrc → persistedUrl → objectUrl → currentSrc → src 回退解析；
- 消息区使用 MutationObserver 兜底：懒渲染、历史恢复或属性更新后出现的图片同样会获得工具条；
- 直接操作类（移除背景）点击即提交，不进入编辑器；画布类工具（标注/评论/擦除/调整尺寸）以对应工具直接打开编辑器；
- 编辑器为模态层：工具切换、笔刷大小、撤销/清除、应用/取消；
- 编辑器在打开时立即完成工具初始化（图片解码前即可交互）；标注文字与评论使用编辑器内联输入（回车或"确定"提交），不使用浏览器原生弹窗；
- 浏览器实测覆盖：画笔/文字标注、评论编号、擦除 mask、移除背景参数、自定义尺寸校验，以及消息工具条的单行布局与直接执行行为；
- 每次编辑先产生一条用户消息（如"移除图片背景"、"将图片调整为 1536x864"、"按标注修改图片"），随后插入 assistant 结果；用户消息与结果都即时出现并持久化，不依赖刷新；
- 提交复用现有图片任务生命周期（`sendImage` 通道、mask 附件参数、任务状态与取消），不新增服务端接口；
- 上游不支持 mask / transparent 等能力时，失败文案为中文可操作提示，内部错误只进日志。

## 6. 安全与隐私

- 原图与 mask 仅存在于内存与既有附件缓存（IndexedDB），不写入会话正文；
- 图片 base64 / mask 数据禁止进入日志（沿用 `image-edit-payload.service` 的脱敏与 multipart 组装）；
- 自定义尺寸严格校验，防止超大画布造成内存问题；
- 编辑器不新增网络调用，仅在用户点击"应用"后走既有图片请求。

## 7. 验收标准

1. 图片消息上显示"编辑"入口，且普通文本消息、不可恢复图片不显示；
2. 擦除：涂抹后可生成与源图同尺寸、含 alpha 的 mask，并成功提交一次 `edit_image`，结果作为新的图片消息返回；
3. 移除背景：一键提交带 `background=transparent` 与 `output_format=png`（或 webp）的编辑请求；
4. 调整尺寸：预置与自定义尺寸均通过校验并随请求携带；非法尺寸给出中文提示且不发送请求；
5. 上游不支持的场景显示中文可操作提示，不暴露内部诊断信息；
6. 普通聊天、生图与既有图片编辑路径不回归。

## 10. 二期：标注与评论

> 状态：二期（标注 / 评论）已实现并通过 `npm run check`；一期（擦除 / 移除背景 / 调整尺寸）已上线。

### 10.1 范围与目标

- 标注（Annotate）：画笔 / 箭头 / 矩形 / 文字四种标注，合成到图片上作为编辑输入图；
- 评论（Comment）：在图片上放置编号评论点并关联文字，合成带编号的图并把"编号 -> 文字"写入提示词；
- 与一期一致：用户在编辑器中的选择是确定性的，直接编译 `edit_image`，不经过意图模型；
- 不新增服务端接口：标注/评论合成图走既有 `edits` 上传与 mask/多图通道。

非目标：

- 不做矢量图层编辑、吸附对齐、多人协作评论；
- 不引入评论持久化（关闭编辑器即释放），评论只作为本次编辑的提示词来源。

### 10.2 流程与状态

```text
图片 -> 编辑 -> 选择"标注"或"评论"
  标注：
    选择子工具（画笔/箭头/矩形/文字）-> 在图上绘制 -> 可撤销/清除
    -> 填写修改指令（必填，描述要如何改）
    -> 合成标注图（原图 + 标注）-> edit_image(target=标注图, prompt=指令)
  评论：
    点击图片放置编号评论点 -> 为每个点输入文字 -> 可删除
    -> 可选填写补充指令
    -> 合成带编号的图 -> prompt = "图中标注 ①：…；②：…" + 补充指令
    -> edit_image(target=合成图, prompt)
```

编辑器状态扩展：

```text
{ annotateTool: 'freehand'|'arrow'|'rect'|'text', shapes: [], comments: [], instruction: '' }
```

### 10.3 契约

- `edit.mode = 'annotate' | 'comment'`；
- 输入图：`edit.annotatedBlob`（PNG，与原图同宽高，由编辑器的合成画布产出）；
- 提示词：
  - 标注：用户指令 + 固定尾注"请根据图片上的标注进行修改"；
  - 评论：由编号与文字组装（`图中标注 ①：<文字>；②：<文字>`），可追加用户补充指令；
- 不携带 mask；单图目标，bindings 与一期一致（target only）；
- 形状与评论点为归一化坐标，合成时按原图分辨率渲染，保证与显示尺寸解耦。

### 10.4 安全与隐私

- 标注/评论只在本地画布合成，不新增网络请求；
- 评论文字与指令长度受限（编辑器侧截断），不进入日志；
- 合成图沿用一期的图片附件链路与脱敏规则。

### 10.5 验收标准

1. 标注工具支持画笔/箭头/矩形/文字，可撤销与清除；应用后合成图与原图同尺寸且包含标注；
2. 评论点按放置顺序编号（①、②、③…），编号与提示词一一对应；
3. 标注与评论提交均为 `edit_image`，target 为合成图，且不携带 mask；
4. 标注模式缺少指令时不发送请求；
5. 失败场景显示中文可操作提示，不暴露内部诊断。

### 10.6 回归测试

- `test/unit/image-editor-workflow.test.js`：标注模式使用合成图作为 target 且提示词包含指令；评论模式提示词包含编号与文字；缺少指令时失败关闭；
- `test/smoke/image-editor-erase-flow.test.js` 保持通过；
- `npm run check` 全量通过（1887 个测试 / 329 个文件）。

### 10.7 实施边界

- 新增：`client/features/image-editor/annotation-layer.js`（形状模型、渲染与提示词组装，纯逻辑可测）；

## 11. 三期：Responses 多轮编辑

> 状态：服务端通道已实现并通过 `npm run check`（默认关闭，不改变现有部署）；客户端会话串联（transport 选择与 previous_response_id 传递）待实现。

### 11.1 范围与目标

- 为图片编辑提供第二传输：Responses API 的 `image_generation` 工具（`action=edit`、`input_image_mask`、`previous_response_id`），对齐 ChatGPT 的多轮高保真编辑；
- 默认关闭：只有部署方显式配置后才启用；生成路径永不受影响；
- 不改变 `dispatch_contract.v1`：契约仍是 `image_edit`，传输选择发生在服务端执行层。

### 11.2 启用方式

- 部署级：`CHATUI_IMAGE_EDIT_TRANSPORT=responses`（`server/config/index.js`）；
- 请求级：图片任务 body 的 `transport` 字段可覆盖（客户端尚未发送，供后续会话串联使用）；
- 前置条件：上游必须实现 Responses API 的 `image_generation` 工具，否则启用后请求会失败；失败保持诚实报错，不回退到 Image API，避免静默改变语义。

### 11.3 契约

请求（POST `{baseUrl}/responses`）：

```json
{
  "model": "<transportModel 或 payload.model>",
  "input": [{ "role": "user", "content": [{ "type": "input_text", "text": "<prompt>" }, { "type": "input_image", "image_url": "data:image/png;base64,..." }] }],
  "tools": [{ "type": "image_generation", "model": "<image model>", "action": "edit", "input_image_mask": { "image_url": "data:image/png;base64,..." }, "size": "1536x864", "background": "transparent", "output_format": "png" }],
  "previous_response_id": "<可选：上一轮 response id>"
}
```

- 仅 `edit_image` 支持；`size/quality/background/output_format/output_compression` 按需传递（`auto` 不下发）；
- mask 只取第一张（与 Image API 语义一致）；
- 响应归一化：`output[].type === "image_generation_call"` 的 `result` → `data[].b64_json`（沿用现有图片结果渲染），`response_id` 随结果返回供下一轮串联；
- 无图片结果时失败关闭（`IMAGE_RESPONSES_RESULT_MISSING`）。

### 11.4 回归测试

- `test/unit/image-edit-responses-transport.test.js`：
  - 传输只对 `edit_image` 生效且默认为 `image_api`；
  - 请求包含 `image_generation` 工具、`action=edit`、`input_image_mask`、目标图 `input_image` 与参数透传；
  - `previous_response_id` 与 `transportModel` 正确转发；
  - 响应归一化为 Image API 形状并保留 `response_id`；
  - 无图片结果失败关闭；
  - job 目标 URL 按传输选择 `/responses` 或 `/images/edits`。

### 11.5 待实现（客户端串联）

- 编辑器/图片任务把 `transport` 与会话内 `previous_response_id` 传给服务端；
- 图片结果写入会话后记录 `response_id`，下一轮编辑自动带上；
- 设置页提供传输选择（默认跟随部署配置）。
