# 26 流式恢复游标与持久化调度设计

> 状态：已实现，待评审。运行中的 Chat Job 以服务端 Job 为权威来源；浏览器只保存有界恢复游标，完整 session snapshot 退回到低频 canonical 边界。

## 1. 范围、事实与目标

本设计解决单浏览器运行多个长输出会话时，pending display 每 500ms 触发整会话 snapshot，导致主线程序列化、IndexedDB 事务排队、超时重试和页面卡死的问题。

范围仅包含浏览器侧流式恢复与持久化调度；不改变服务端 Job、SSE API、principal、dispatch contract 或图片任务 schema。

已确认事实：

- 服务端 Job 保存运行中的权威正文和思考内容，并支持从 offset 重放。
- canonical `messages/display` 已由 `openapi-chat-session-db-v2` 持久化。
- 旧 pending checkpoint 会构建完整 `messages + pendingDisplay`，同步写 localStorage fallback，并多次深拷贝后写 IndexedDB。
- 主线程被长任务占用时，IndexedDB 完成回调、定时器和场景无法及时推进；扩大超时不会改变根因。

目标：

1. pending 流状态写入成本只与本次有界增量/尾部有关，不与整个会话历史线性相关。
2. 每个 session 最多保留一个待写 cursor，新的状态覆盖旧的待写状态，不形成无界队列。
3. 刷新后可在服务端 Job 存在时精确恢复全文；服务端 Job 不存在时只恢复有界尾部并明确按中断态处理。
4. cursor 写入失败不重置 canonical session snapshot 的连接，不产生全局重试风暴。
5. 三个以上长输出会话下，主线程仍可输入、滚动和绘制。
6. 流式 token 不得把完整正文或思考内容反复写入 DOM data attribute；DOM attribute 只在终态发布一次，流式全文保存在消息节点内存属性中。

## 2. 分层与数据所有权

| 层 | 所有者 | 生命周期 | 内容 |
| --- | --- | --- | --- |
| hot | 内存 aggregate / DOM | 当前页面 | 实时正文、思考、渲染节点 |
| warm | `stream_checkpoints` IndexedDB store | Job 未终态 | 有界 cursor、尾部预览、恢复身份 |
| canonical | `sessions` IndexedDB store | 已完成/显式保存 | 完整 message 与会话事实 |
| pointer | localStorage Job key | 任务交接/恢复 | job id、payload、display 绑定信息 |

规则：

- pending display 不再作为完整 session snapshot 的高频写源。
- `resume_cursor.v1` 不是正文权威副本，不得覆盖 canonical message。
- 服务端 Job 存在时，服务端 aggregate 优先于 cursor 内容。
- 服务端 Job 缺失时，cursor 只能恢复为 partial/interrupted 投影，不得伪造完成态。

## 3. `resume_cursor.v1` 契约

存储：IndexedDB 数据库 `openapi-chat-stream-checkpoint-db-v1`，object store `stream_checkpoints`，按 `sessionId` 存储。

```text
resume_cursor.v1 {
  version: 1
  sessionId: string
  updatedAt: number
  items: [{
    id, role, rawText, reasoningText, html: ''
    messageIndex, responseIndex, messageId, turnId, replyToMessageId, jobId
    imageContext, attachmentContext, quoteContext, metaText
    outputStarted, pending: '1'
    streamCheckpoint: {
      version: 1
      contentLength, reasoningLength
      contentTailStart, reasoningTailStart
      tailOnly
    }
  }]
}
```

约束：

- `rawText` 与 `reasoningText` 默认分别最多保留 65536 / 32768 UTF-16 code unit。
- 单 session 的 cursor 总文本预算默认不超过 131072 code unit，item 数默认不超过 32。
- `html` 不进入 cursor。
- 大体积 `data:` URL 和超长 metadata 必须被替换或有界截断。
- cursor 不得包含完整 canonical `messages` 数组。

## 4. 写入与调度

```text
SSE delta
  -> aggregate（即时）
  -> DOM 更新（active session，节流）
  -> checkpoint dirty
       -> per-session latest-wins
       -> 500ms 合并窗口
       -> 单 writer 批量写 IndexedDB
terminal
  -> canonical commit
  -> cursor delete
```

规范：

- `checkpointSessionDisplayItem` 只标记 dirty 并调度 cursor，不调用完整 `commitSession`。
- 恢复 SSE 的历史重放帧先按 session 做 latest-wins 合并（默认约 32ms）再进入 display/DOM 热路径；终态或异常前必须先 flush 该 session 的最新非终态帧，再提交 canonical 结果。
- `takeChatJobLiveItem` 只能修补 pending item 并调度 cursor，禁止顺带提交完整 session snapshot。
- busy 页面离开只 flush cursor、会话元数据和已有 writer，不得为当前 active session 追加 `saveDisplayHistory` / `saveChatHistory` 两个 canonical 序列化边界。
- 同一 session 的连续更新只保留最新 cursor；旧待写值可安全丢弃。
- writer 串行提交小批量，一次 IndexedDB readwrite transaction 可包含多个 session。
- checkpoint 基线为 500ms；活跃流达到 4 路时退避到 1000ms，达到 8 路时退避到 2000ms，避免多个会话同时竞争持久化。
- 写入失败只重试该 cursor 批次，采用有上限退避；未超过重试上限前不改变 UI 任务状态。
- 不得因为主线程延迟触发的 watchdog 关闭共享 canonical DB 连接。
- 页面离开时先 flush 最新 cursor；写入未完成不得阻塞 canonical 保存或卸载流程。

## 5. UI 热路径纪律

- 流式全文保存在消息节点内存属性，DOM `data-raw-text` / `data-reasoning-text` 只在终态发布一次。
- display item 到 DOM node 的查找必须缓存当前连接节点；节点脱离后再重新查找。
- pending item 的第一帧完成 canonical 放置，后续 token 复用 placement key，不得重复扫描完整消息列表。
- actions 状态未变化时不得重建或重新绑定消息按钮。
- 正文未变化时 reasoning 不得重复渲染；只有 reasoning 内容或终态变化时才进入渲染器。

## 6. 刷新恢复

优先级：

```text
canonical terminal
  > 服务端现存 Job
  > resume cursor
  > 无恢复
```

流程：

1. 加载 canonical snapshot 与 cursor，按 display item id/jobId 合并，cursor 覆盖旧的 pending 投影。
2. 标记 `streamCheckpointRecovered=true`，若有截断再标记 `streamCheckpointTailOnly=true`。
3. 初始 UI 只把 cursor tail 当作 provisional preview。
4. chat resume 从服务端 offset 0 重放；首次 GET 返回的 running 快照必须先落为当前前缀，再据此计算后续 SSE offset。tail-only cursor 不得在 provisional 更新尚未应用时被当作完整前缀。
5. 若 localStorage 任务指针丢失但 cursor/display 中仍有 Job id，resume 允许这个 display-only 指针直接 GET/SSE 跟随服务端现存 Job；它没有本地 payload 和 dispatch contract，因此绝不允许用于重新 POST 任务。包含任何本地执行快照字段的指针仍必须先通过 final execution contract 校验。
6. 收到服务端首个有效 aggregate 后，用服务端 full content 替换 provisional preview，并清除恢复标记；该替换必须先于 SSE offset 计算和订阅。恢复出的 wait/SSE 必须绑定 active run 的 AbortSignal 与 runToken，使停止按钮立即生效并抑制迟到更新。正文与思考继续共用同一个 aggregate、display item 和 live update 入口；不得为空正文增加独立轮询或第二套 reasoning 恢复路径。
7. 服务端返回 Job 不存在时，只能进入 partial/interrupted 错误路径；不得把 tail 提交为完成消息。清理必须同时删除 localStorage Job 指针和 display 中相同 jobId/responseIndex 的 pending 投影，否则下一次刷新会反复查询同一个幽灵 Job 并产生 404。

## 7. 失败、降级与安全

- cursor read/write 失败对用户表现为可恢复任务降级，不把内部 `IDB_OPERATION_TIMEOUT` 暴露到消息气泡。
- canonical 提交失败继续使用 03 定义的 recoverable fallback；cursor 只是附加恢复来源，不能替代 canonical 持久化。
- cursor 可能包含用户文本，必须与 session 数据同级保护：不进入日志、trace、导出备份或服务端。
- 大 base64、blob URL 和签名 URL 不得进入 cursor 日志和错误消息。
- 终态清理必须是幂等的：先完成 canonical commit，再删除 cursor；重复删除不报错。

## 8. 验收标准

1. 三个 session 同时持续输出长文本时，pending checkpoint 不触发完整 session snapshot。
2. 每个 session 在任何时刻最多保留一个待写 cursor；写入量与增量相关，不随历史消息总量增长。
3. 长输出 cursor 的正文和思考尾部保持有界，且不含 HTML、完整 messages 或大 data URL。
4. 刷新后服务端 Job 存在时可以无重复地恢复全文；cursor 仅用于 provisional preview。
5. 服务端 Job 不存在时不会伪造完成态。
6. cursor 写入失败不会关闭 canonical DB 连接或造成跨 session 重试风暴。
7. 终态 canonical 提交成功后 cursor 被清理；完成答案不残留在 pending display。
8. 流式正文和思考不得在 token 路径中改写完整 `data-raw-text` / `data-reasoning-text`，也不得持续触发以这些属性为过滤条件的 MutationObserver。

## 10. 实施映射

- `client/services/stream-checkpoint-store.js`：`resume_cursor.v1` 编码、裁剪、合并、latest-wins writer、IndexedDB store。
- `client/app/session-display.js`：pending 路径接入 cursor；load/delete/clear/flush 与 canonical store 协同。
- `client/app/job-resume-workflow.js`：tail-only cursor 使用 offset 0 重放，收到服务端内容后清除 provisional 标记。
- `client/app/message-workflow.js` 与 `client/app/reasoning-workflow.js`：流式全文保持在节点内存属性，DOM data attribute 仅终态同步。
- `client/app/display-history-workflow.js` 等读取方优先读取内存属性，兼容旧 DOM attribute。
- `docs/design/03`：补充 cursor 与 canonical 的分层。
- `docs/design/25`：修正“EventSource 数量即浏览器容量”的表述，增加端到端长流 profile。

## 11. 纯思考恢复展示约束

刷新恢复收到仅包含思考内容的运行帧或终止帧时，客户端必须将该帧提交到聊天流式展示路径；终止帧不得只刷新待处理队列而丢弃当前思考内容，且恢复增量必须携带会话与聊天流类型标识。
